怎么测 decode

这个仓库里有两套 harness 都会产出解码数字，而任何把两者放在一张图上的做法， 都需要它们之间的差异是一个数，而不是一个假设。它是 0.44 % —— 前提是机器已经热了。 搞清楚这一点花了四次相同的运行，其中第一次低了 31 %。

摘要

campaign 那套 harness 驱动一个 OpenAI 服务、走流式、温度 0.8 采样，在 512 token 的一次生成上报数。探针那套离线驱动 LLM.generate、greedy， 用 64 token 的一次运行减 8 token 的一次。在对齐的深度上，两者相差 0.44 %、0.01 %、0.07 %，而把生成长度也对齐并不改变任何要紧的东西。 它们是同一次测量。

走到这一步需要先发现：在这台机器上，一次运行不构成一次测量。 四次相同的运行连着跑，读数是 −30.7 %、−5.1 %，然后收敛；而且亏得最多的正是机器最快的那些点， 这也是它一开始看起来像"两套 harness 不同"而不是"预热效应"的原因。

由此得出两条规则，写进 ledger 里，而不是留给画图的人。每个点都带 runs 和 range_pct；而 patches 是一个列表而不是布尔值， 因为一个需要未合并 PR 才能拿到的点，和一个装上发行版就能拿到的点，不是同一个断言。

报的是极差而不是标准差，有一个格子说明了为什么。给一个 8K 上双峰的点加上第三、 第四次运行之后，它的极差从 15.79 % 变成 16.79 % —— 变宽了 —— 而它的标准差从 4.87 降到 3.61。一个统计量说这个格子变得更不可信，另一个说它变得更可信。

1两套 harness 测的是不是同一件事

标定用的模型是特意挑成对这里其他每一个变量都免疫的，这正是选它的全部理由：

    引擎参数用的是 campaign 的那一套，深度用的是 campaign 自己报出来的 prompt_tokens 而不是标称目标，这样两边坐在同一个上下文上，而不只是相近。

    2那三次多花的运行，以及它们换来了什么

    第一次做图 1 时，探针在最短深度上比 campaign 低 31 %，在最长深度上低 9 % —— 一个听起来很有道理的差异，因为两套 harness 在长度、采样和传输上确实不同。这三样都不是原因。

    为什么这不会追溯性地损害那些 campaign 结果 campaign 的每一个格子都起一个全新容器，而它的引擎初始化 —— 加载模型、编译、图捕获 —— 在任何计时开始之前就要花上几分钟；而且 campaign 本来就每格跑两轮，两轮一致到 0.2 %。 另一个实验里把两臂顺序对调的那一对在 1K 上一致到 0.3 %、32K 上 0.2 %， 而这么大的首格惩罚会把它打破。由此得出的规则是给探针运行的： 从冷机器开始时，第一次要丢掉，而不是平均进去。

    3跨越五周的那个对照

    两次 campaign 相隔五周，内核不同、补丁不同 —— 而有六个配置在两边都测过。 这六个是唯一能说明"七月的数字和八月的数字能不能放在同一张图上"的东西。

    4每个点都带什么，以及线画在哪

    ledger 是把原始文件投影到一种行格式上的产物，它是被重新生成并比对的，不是被编辑的。 有两样东西跟着每一个点走，因为把它们留给图表，正是一个仓库开始承诺超出自己实测范围的方式。

    5为什么报极差而不是标准差

    这里几乎每个格子都只有两次 run。在 n=2 时，样本标准差就是极差除以根号二 —— 同一个数字，披了一件它没挣到的分布外衣。到 n=4 才开始有点意义， 而论证也正是在那里变得具体，因为恰好有一个格子有四次。

    6为什么比对输出不是这里的正确性测试

    检验一个 kernel 改动是否无害，最直觉的办法是比较改动前后生成的 token。 在这台机器上，那测的是机器，不是改动。

    所以这个仓库里的数值主张，是在定输入上对着 fp32 参考实现做的； 端到端的改动则是从速率和从 worker 内部记录的路由来论证的。 比对 token id 只用在已知具有确定性的平台上 —— 而实测下来，那是 A100，不是这台机器。

    7没有被确立的部分

    第一次运行为什么慢

    效应被测到了，形状也描述了；机理没有。它挺过了一次预热生成，不局限于第一个深度， 并在第三次运行时收敛。究竟是宿主、驱动、容器还是别的什么，没有被隔离出来。

    两套 harness 在其他模型上是否一致

    标定只有一个模型，而选它正是因为这个仓库里没有其他变量能碰到它。 这让对比干净，也让它变窄：一个走不同 kernel 路径的模型，可能因为这里什么也没说的原因而在两套 harness 之间不同。

    两个没落进带子里的对照

    六个配置里有两个在两次 campaign 之间动了约 0.8 %，其中一个是另一项调查的主题， 那项调查排除了若干候选而没找到原因。所以跨 campaign 合并是带着一个带宽陈述的， 而不是断言等价。

    greedy 输出里变的是什么

    这里没有主张任何一个变化了的输出是错的，只主张它们不可复现。 TP=1 没测，而源头在 kernel 之上，但没有进一步定位。

    8此后发生的变化

    2026-08-26 · 第一次标定尝试才是有意思的那次 它拿一次探针运行去对比 campaign，得出了 31 % 的 harness 差异，而且现成就有一个像样的解释。 再跑三次把它变成了一个预热效应。这篇文章要讲的那条规则 —— 在这里一次运行不构成一次测量 —— 正是从差点发表相反结论里来的。
    2026-08-29 · 那道线的理由被重新陈述 build_ledger.py 论证它 6 % 的阈值时，描述的是规则写下来那一刻的散布分布。 那个分布动了：0.27 的行进来了，双峰那个格子多了两次 run，于是尾巴现在是 2.6、3.4、3.5、4.1、5.1，然后跳到 16.8，而这道线排除的是一个点而不是两个。 注释现在描述的是当前分布，而验证器把它的尾巴钉住了，所以它不会再无声地过期。

    自己跑一遍。标定探针和它的四轮在 benchmarks/harness-calibration/； ledger 和构建它的规则是 ledger.jsonl 与 build_ledger.py —— 后者在入库投影与其来源不再一致时会失败；非确定性记录是 gfx1100-greedy-nondeterminism.json。 本页每一张图都由 verify_doc_figures.py 从这些文件重算。

    非确定性已贴到 vllm#50603， 那份报告说的是同一个 Triton 兜底路径的同一个症状，但称一次预热调用能修好它 —— 而这里每一次测量都已经带了预热，仍然会变；所以要么那个办法不通用，要么这是第二个缺陷。
