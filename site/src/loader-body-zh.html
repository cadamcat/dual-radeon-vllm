RDNA3 · KFD · HMM · 实测于 2× RX 7900 XT

加载权重比磁盘还慢，
而且慢了两次

一个 9.56 GiB 的 checkpoint，磁盘大约六秒就能交出来，实际用了 328 秒。两个彼此独立的原因：一个权限 bug，让 GPU 去要它并不需要的写权限 —— AMD 已确认并定位到内核某一行，今天依然存在；另一个是发行版的 backport， 把这个 bug 的每一次触发都变成整整一秒 —— 用 revert 证明，Canonical 五周后修好。

2× RX 7900 XT · gfx1100 · VFIO 直通 Ubuntu 7.0.0-28 → -30 ROCm 7.14 · safetensors 0.8.0 实测 2026-07-28 与 2026-08-23

摘要

第一个效应是权限取错了地方。host→device 拷贝只会读源， 但 KFD 是从 VMA 的 flags 推出它要申请的访问权限；于是带 VM_WRITE 的映射 会让 hmm_range_fault() 去要写权限，从而在每一个常驻页上破坏 copy-on-write。 PyTorch 把 safetensors checkpoint 映射成可写的，因为 storage 必须可变 —— 所以这是所有框架都会走的那条路。AMD 确认了它并给出了行号。在今天在跑的内核上，它值 4.8×。

第二个是一次 backport。Ubuntu 的 7.0.0-28 取了 c08972f55594 却没取它的后续 342981fff328， 留下一个会空转满 HMM_RANGE_DEFAULT_TIMEOUT 的重试循环。 于是每一个计时都落在 1000 ms 的整数倍上：一次 32 MiB 拷贝要 16 019.6 ms，也就是十六个窗口加 19.6 ms 的真实工作。 只把缺的那个 commit 加回去重编 amdgpu.ko，结果是 17.0 ms。 Canonical 在 2026-08-20 随 -30 发出来，同一个复现器现在是 15.3。

这一对自己解释自己：破坏 copy-on-write 正是推进 notifier 序列的动作， 所以权限 bug 是触发条件，而缺失的那个 commit 把每次触发变成整整一秒。 只读映射永远不会失效，也就永远不会进那个重试。

本仓库自己的一个数字没有活下来。随 vllm#49991 发出的 3.9×–5.6× 来自一次没有控制 page cache 的运行。逐格控制缓存重测之后：checkpoint 装得进内存时是 1.5×–2.0×，装不进时是 7.5×，而在一个 128 专家的 MoE 上略微为负。

1这个问题，以及它是从什么上面问出来的

开头那次测量是全文最弱的一个，而它又是后面一切的起点，所以先把它连同出处一起放在最前面。 2026-07-24，用 dd iflag=direct 在同一个文件上测得磁盘 1.5 GB/s， 一个 15.6 GiB 的 BF16 checkpoint 以 77 MB/s 加载，一个 9.56 GiB 的 w4a16 是 29。 比它自己躺着的那块介质慢十九倍和五十二倍。

这两个数字是从哪来的 这两行来自 docs/open-questions.md §8 的历史记录部分，没有对应的入库数据文件。 它们提出问题，不确立任何东西。从图 1 起的每一个数字都对着入库文件测过， 都可以重算。那份文档的小节标题写的是 19–48× 而不是 19–52×， 因为它除的是十进制 MB 速率而表格里写的是 MiB/s —— 那边已标注， 而且与答案无关：答案是直接测出来的，不是从一个比值推出来的。

第一次给出的原因是错的，值得说，因为它塑造了之后的方法。本仓库曾发表过 "源是一个 file-backed 的 mmap 页，而 ROCm 对这种页不走 pinned-staging 路径"。 一个不依赖任何东西的复现器推翻了它：普通 mmap 一个热文件全速拷贝， 而八个能想到的变量 —— 匿名对 file-backed、已 fault 对未 fault、每次拷贝换新 range、 overlayfs 对 ext4、每次拷贝换新设备分配、1–256 MiB 尺寸扫描、页不对齐的起点、dtype —— 一个都触发不了。此后对第二个原因的门槛就变成了：一个陌生人能跑出同样的结果。

2真正会触发它的那个变量

同一个文件在同一个进程里的两个映射，此时 safetensors 正打开着一个 checkpoint：

/proc/self/maps
75d757200000-75d845520000 rw-p ... model-00001-of-00005.safetensors   <- safetensors
75d468a00000-75d556d20000 r--p ... model-00001-of-00005.safetensors   <- 我们的

一个只读的 checkpoint 被 MAP_PRIVATE 且可写地映射。 把这一个变量单独拿出来 —— 同一个文件、同样的字节、普通 mmap 加 torch.frombuffer，不用 safetensors 也不用 vLLM —— 三十行就能复现全部现象。 再加一个维度：CPU 在拷贝之前有没有碰过这块映射 —— 会得到三种状态而不是两种， 而真实的加载落在第三种里。

16 019.6 ms 不是带宽数字，也不是噪声。它是十六个 1000 ms 的 HMM_RANGE_DEFAULT_TIMEOUT 窗口加 19.6 ms 的真实工作； 那份看起来像固定每页开销的亚毫秒级可重复性，其实是一个 jiffies 超时。 一旦能这样读这个数字，其余的就都顺下来了：两种文件系统之间那个平坦的一秒差距是多了一次重试， 而每个张量 1005、1042、1522 ms 分别是一个、一个、一个半窗口。

3为什么一次读会去要写

AMD 在 ROCm#6523 上确认了机理并指出了位置。这条链在上游代码里是三跳：

权限是从 VMA 取的，而不是从 GPU 接下来要对这段内存做什么取的。 host→device 拷贝只读源。但因为 VMA 带着 VM_WRITE，KFD 就向 hmm_range_fault() 要写权限，于是每一个常驻页上的 copy-on-write 都被打断。 这就是永久的那一半，它在这里测过的每一个内核上都在，而那一行比它们都老。

它也不需要任何额外假设就解释了那三种状态：CPU 没碰过的页还没有进入 copy-on-write 共享， 所以"未常驻"那一档从来不用为打断付费。它还把两半接了起来：破坏 copy-on-write 正是推进 notifier 序列的动作，所以只读映射永远不会失效、永远不会拿到 -EBUSY、 也就永远不会进 c08972f55594 留下的那个空转重试。

可写映射不是 safetensors 干的 safetensors 是只读映射 —— map_copy_read_only，用 framework="np" 能看到 r--p。它的 PyTorch 路径根本不用那个映射： 它调的是 torch.UntypedStorage.from_file(filename, shared=False, nbytes=size)， 而 PyTorch 把文件映射成可写的，因为 torch storage 必须可变。所以任何框架从 safetensors checkpoint 经 PyTorch 路径加载的每一个张量，背后都是 rw-p。

4被拆开的那个 commit 值多少，以及是谁修的

342981fff328 既没有 Fixes: 标签也没有 Cc: stable@vger.kernel.org，所以从未进入 stable 队列；而 c08972f55594 进了 -28。一个没打标签的修复，不会跟着它修的那个 commit 走。 所以这不是发行版打包的疏漏，而是上游打标签的缺口，任何跟着 7.0.y 走并取了第一个 commit 的分支都处在同样的状态。

四种配置、一个复现器，只有一个是慢的：同一台 guest 在 7.0.0-28 上十六秒， 同一台 guest 在 7.0.0-14 上 18.6 到 20.2 ms，6.8.0-136 上 22.1 到 26.0， 以及裸机上一个 Proxmox 7.0.14 构建的 24.1 到 28.6。 关键是前两行：同一台 guest、同一套 ROCm 用户态、同一个容器镜像、同一个复现器， 只换了内核 ABI。直通不是必要成分，而那本来是这边和 AMD 那边共同的首要怀疑对象。

这份报告不是修复的原因 linux-hwe-7.0 于 2026-08-20 在 noble-updates 和 noble-security 里升到 7.0.0-30.30~24.04.1，带上了 drm/amdgpu: drop retry loop in amdgpu_hmm_range_get_pages。而那个专门请求这次 backport 的 Launchpad bug 至今仍是 New、未经分诊，所以这个 commit 是走普通 stable 流程进来的。 在 24.04 上现在的解决办法就是升级，图 1 里那个重编的模块是证据，不是建议。

5永久的那一半值多少

第二个效应消失之后，第一个才第一次能端到端量出来。四个 checkpoint、四条加载路径、 逐格控制 page cache —— 每一格要么先 drop_caches，要么 drop_caches 之后再把整个 checkpoint 完整读一遍 —— 每格一个新进程。

孤立的测量脚本是偏乐观的那一个，高出 10 到 14 %。在 12B 上做一次真实的 vllm serve 启动，读加载器自己那行 Loading weights took， 热缓存是 1.79×、冷缓存 1.52×，而上面的脚本给的是 1.98 和 1.73。 绝对秒数是贴合的，这正是那个脚本还能用的原因；但比值不贴合，因为一次服务端启动还带着脚本没有的工作。 把图 2 里的倍数当成这个开关值多少的上界来读。

这张图里有三件事值得明说。31B 冷缓存那一格是 7.5×，因为 21.67 GiB 的 checkpoint 对上 23.4 GiB 内存，丢掉的不只是 copy-on-write，而是把加载器逼进了 swap。 MoE 那一格是反例：一个由 35 743 个多数很小的张量组成的 checkpoint 里， 几乎没有什么大到需要付 copy-on-write 的代价，于是多出来的那次主机拷贝纯属开销， 这个开关比什么都不做还略差。而 pread 从 safetensors 0.8.0 起就有了， 只在 release notes 里提过一句，它在这里除了 MoE 之外都比 clone 慢，而在 MoE 上最快。

6机理，就在常驻集里

为什么这个惩罚不是一个固定比例 —— 只要在加载过程中采样常驻集，就能直接看到， 而不必去推。safetensors 在迭代器离开一个 shard 的瞬间就把它 unmap 掉， 所以循环结束时再采样只会看到一个空进程；第一次这么做什么也没测到，那次数据被丢弃了。

7没有被确立的部分

为什么七月的基线复现不出来

在 -30 上不做缓存控制、按 2026-07-28 的顺序重放一遍，8B 的 baseline 是 13.87 s， 而当时报的是 36.4 s；31B 是 126.61 s，而当时是超过 900 s 的超时。 所以 page cache 不是全部解释。两次之间变了两件事：内核状态，以及这台 guest 的 PCIe atomics —— 七月是关的，现在是开的。32 MiB 的复现器在同一次变化里只从 17.0 动到 15.3 ms， 所以差别不在每次拷贝这条路径上，但这里没有任何东西说它在哪。七月那张表是被取代，不是被调和。

一台机器，而且是虚拟机

这里的一切都是一台 VFIO guest、gfx1100、ext4。裸机上的 Ubuntu -28 是别人替我们关掉的 —— @shineday999 报了一台 RX 7900 XTX、ROCm 7.2.1、没有虚拟化， 同样的病理和同样的整数窗口数 —— 但 Canonical 原样发的模块在裸机上如何，仍未测过， 因为我们两边跑的要么是自建模块、要么是用户态绕过。CDNA 没测， 而且这里没有任何数据说得出在一台内存远大于 checkpoint 的宿主上这些还值多少。

每个张量的常驻程度

窗口数是 resident_bytes / 2 MiB，由复现器在 32 和 256 MiB 上确立， 并在另一块板子上被独立确认。"一个 8 MiB 的张量和一个 96 MiB 的张量都只出一个窗口" 这一步是从中推出来的 —— 拷贝开始时它们几乎都不常驻，因为在此之前没有任何东西读过它们 —— 但每个张量的常驻程度从来没有被直接采样验证过。

两个 rank 之间 17 倍的不对称

某一次加载里，一个 rank 每次 ioctl 约 190 ms，另一个约 11 ms。 用并发进程、内存压力、torchrun 加 RCCL 都没能复现，至今没有解释。

8此后发生的变化

2026-08-23 · 那个开关的头条数字被撤回 vllm#49991 发表的是一个平坦的 3.9×–5.6×，并称这个量级是永久的。它来自一次没有控制 page cache 的运行， 那次连续加载了三个模型，于是每一格都继承了前一格的缓存。逐格控制缓存重测之后： checkpoint 装得进内存时是 1.5×–2.0×，装不进时是 7.5×。那个 PR 还说 "在测过的每一种配置下 clone 都更快，默认打开看起来是合理的"； 图 2 里的 MoE checkpoint 就是反例，那句话必须去掉。
2026-08-20 · Canonical 发出了缺失的那个 commit 7.0.0-30.30~24.04.1，在 noble-updates 和 noble-security 里。 那些一秒的窗口没有了：同一天、同一台机器、同一个复现器二进制， 升级前 16 019.3 ms，升级后 15.3。 ROCm#6523 上有这次测量。
2026-07-30 · 裸机那个缺口被一个陌生人补上了 这份报告没法测非虚拟化的机器。@shineday999 跑了一台 —— RX 7900 XTX、ROCm 7.2.1、 7.0.0-28、没有虚拟化 —— 报出了同样的病理和同样的整数窗口数， 随后又补了一份逐张量的分解，四次独立运行落在四个整数窗口上。 两个 ROCm 版本一致，也说明用户态版本不是变量。
仍然开着 可写映射这个惩罚本身没有被上面任何一件事碰到，在 -30 上值 4.8×。 ROCm#6523 开着； vllm#49991 开着， 它的头条数字需要换成上面那个实测区间。ROC_FORCE_STAGED_D2H 本可以完全绕开这次拷贝，但 @ashetaia-amd 说 ROCm/rocm-systems#6676 里采取的长期修复对这条拷贝路径没有帮助，所以那不是可以等的解药。

自己跑一遍。复现器是 benchmarks/repro-mmap-prot.py， 没有 PyTorch 的机器可以用 repro-mmap-prot.hip.cpp。 图 1 是 hmm-kernel-three-states.json； 图 2 和图 3 是 loader-flag-kernel-30.json， 89 格，每格都带自己的 page cache 状态。完整的调查过程，包括本仓库第一次搞错的那个成因，在 open-questions.md §8。
