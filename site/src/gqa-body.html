A gate that costs 2 to 7 times and buys nothing

On gfx11, vLLM's ROCm custom paged-attention kernel is enabled only when the query-to-KV head ratio is at least 3. In the excluded range the same kernel is 1.70× to 7.28× faster than the Triton fallback it is passed over for, and numerically equivalent to it inside what bf16 gives for a sum this long. Sixty cells, two vLLM versions, no exception.

Abstract

The bound came in with vllm#17004, whose own description says the kernel "supports gqa_ratio up to 16, and shows performance gains over the existing kernel when gqa_ratio is 3 or higher". So it is a performance heuristic, not a capability limit, and the CDNA branch of the same function runs the same kernel from ratio 1. Both are still true on main.

Tested, the heuristic is inverted here. Across sixty measured cells — five shapes, six context lengths, two vLLM generations — the custom kernel is faster in every one, and the excluded band overlaps the admitted band on both versions. There is no region the bound separates.

The report that prompted this, vllm#50603, also blames the fallback for losing accuracy at long context. That is not supported: across 90 cells on two architectures relative error stays between 2.12e-3 and 4.72e-3, and no two depths' pooled medians differ by more than 1.09×. A flat band only means something if the instrument can see a fault, so the same harness was given one: NaN in the unwritten tail of the final KV tile poisons both paths, at exactly the lengths that straddle it and no others.

End to end on a real model the one-line widening is worth 1.02× at 1K and 1.17× at 32K, reproduced in both run orders on the newer image. That is vllm#54210, and this page is what it rests on.

1What is being measured

Both paths are driven through vLLM's own chunked_prefill_paged_decode dispatch with only use_rocm_custom_paged_attention forced, so nothing about argument marshalling differs between the arms. Pure decode: one query token per sequence over a fully cached context, which is the shape the report describes. The reference is fp32 and is computed from the pre-paging KV rather than from the cache, so a paging bug cannot cancel itself out. Scoring is relative L-infinity against the reference's own scale, which is what makes different lengths comparable.

The shape set covers ratios 1, 2, 3 and 4 at head size 128 and block size 16, plus 32/16, which is gemma-3-27b-it's real shape and satisfies every condition of the gfx11 gate except the ratio. The CUDA control compiles the same Triton text: the kernel is lifted verbatim into a standalone module and the launch mirrors the dispatch's argument list.

2Sixty cells, and no exception

The bands are the argument, not the maxima. On 0.23.1 the excluded ratios span 1.84× to 7.28× and the admitted ones 2.35× to 7.40×; on 0.27 it is 1.70× to 6.05× against 2.20× to 6.05×. The two overlap on both versions, which is what "the bound does not separate anything" means in one sentence.

3The accuracy claim, and the control under it

The originating report describes two symptoms. The first, the fallback being taken at all, is exactly right and is what everything above is about. The second is that the fallback degrades with context. That one is testable here and does not hold.

A clean sweep is worth nothing if the instrument is blind Two things the sweep above does not exercise: every length is a multiple of the block size, so the final KV tile never straddles the sequence end, and the cache is zero-filled. Filling it with NaN and using lengths that straddle produces the fault on demand — and only there.
Only NaN propagates: finite garbage at 1e4 is handled correctly by the score mask alone, which is why this is subtle. Both paths poison identically on this version.

4What widening it is worth on a model

Kernel microbenchmarks are not what a pull request has to justify. gemma-3-27b-it-w4a16, TP=2, CUDA graphs on, decode by 64-against-8 differencing, one fresh container per cell so the source edit cannot leak between arms:

Routing is recorded from inside the TP workers rather than inferred, in every cell. The full-attention layers arrive with head size 128, block size 16, the native KV layout and a power-of-two block, so the ratio is the only gate condition they fail; the sliding layers fail on sliding_window == 0 in both arms and never move.

Two things this measurement is not Output equality between arms is not the correctness test. Greedy decoding on this box is not reproducible across processes for this model, so comparing token ids would measure our own nondeterminism instead. The numerical case is Figure 2's, against an fp32 reference. And the first attempt's kernel counter was blind, because TP=2 runs attention in spawned workers where a parent-process counter sees nothing.

5What widening it would also admit

Opening a gate lets in whatever is behind it. vllm#53856 fixes a real fault in the same custom kernel: it masks logits past the sequence end but its vectorised V-cache load still consumes the whole final block, so an unwritten NaN in the tail poisons the output. Its test plan says gfx11 received compile validation only, because the author had no such device.

The forced column is the one that bears on the proposal. Past the gate, the stock arm poisons eight cells rather than four: ratio 2 fails identically at the straddling length, both dtypes, V-only and K+V. All eight are clean on the patched arm. So widening the gate admits ratio 2 to this kernel, and this is the fault it would admit with it — which is why the two threads belong together, and why the gfx11 runtime evidence went to that PR's author on request.

6What is not established

The report's second symptom

What is removed is one hypothesis — that the Triton 2D kernel loses accuracy as context grows. The reporter's model is a VLM this project does not have, on hardware it does not have, and this measures the kernel rather than their output. Their symptom still needs an explanation.

Everything outside pure decode at these shapes

Sliding-window shapes, fp8 KV, prefill shapes and TP>1 at the kernel level are all untested here. The end-to-end measurement is TP=2, but that is a model measurement, not a kernel one.

Where the NaN comes from

allocate_kv_cache zero-fills the backing allocation, so it is not fresh-allocation garbage; vllm#53856 attributes it to sleep mode and allocator behaviour. This probe injects it deliberately and only measures what the kernel then does.

One machine, and the model runner question

Everything here is one gfx1100 box. A related question — whether Model Runner V2 reaches the same guard — was measured on this hardware: it does, on 36 of 37 rows identical to V1. Whether speculation makes decode carry more than one query row under MRv2 could not be measured, because no checkpoint here configures for it on that image. That half rests on a code read.
