摘要

这篇文章原来问的是一个问题 —— 两张消费级卡对一张 A100 —— 而这个问题里其实捆着三个。这一轮把每张卡单独测了一遍，于是三个问题分得开：一张消费级卡对一张数据中心卡值多少， 第二张消费级卡再买到什么，然后才是这一对值多少。

第二张卡在解码上几乎不起作用。横跨十一个深度、两个模型，它买到 1.11× 到 1.23×。batch 1 下一步解码既是带宽受限又很短，而 TP=2 每一步都要付一次固定的 all-reduce，所以第二张卡的带宽大半花在了跟第一张说话上。而在 prefill 上同一张卡买到 1.56× 到 1.87× 的墙钟时间，因为 attention 的并行完全不需要通信。

prefill 是两项，而且两项不同向。拟合 T(S) = a + bS + cS²，对一张 7900 XT， A100 在稠密的 12B 上是 b 3.3×、c 6.7×：attention 尺度上的差距是算力差距的两倍。 而在 MoE 上——它每个 token 只激活 26B 里的 4B，算力项本来就小——两个差距一样大， 5.75× 与 5.71×。至于 L4，一张数据中心卡，在 b 上比消费级的 7900 XT 还慢（0.90×），在 c 上好 3.0×。「数据中心对消费级」根本不是一条轴。

这一对对一张 A100 是第三步，也是这篇文章最初站的地方。不带投机时，A100 在一套十一档的阶梯上 每一档都领先 1.30× 到 1.46× —— 平的，完全不是四个单次点暗示的那个 U。

1比的是什么

四台机器：一张 RX 7900 XT、两张、TP=2、一张 A100-SXM4-80GB 和一张 L4。三个模型，而且不是每个模型都在每台机器上都有， 因为其中两处缺口是算术，不是遗漏。gemma-4-26B-A4B 在一张 7900 XT 上到 12 000 token 为止：16.96 GiB 权重驻留在一张 19.98 GiB 的卡上，即使 util 开到 0.95 也只剩 0.93 GiB 的 KV， 要到 32 K 得开到约 0.97。而 gemma-4-31B-it 根本没有单卡这一行 —— 22 GB 的权重塞不进一张 20 GB 的卡，所以这台机器上只能用一对卡跑它。31B 因此是第三步的模型， 在那之前的任何一步里都不出现。

解码和 prefill 各自取自哪里 前三步只要同一次运行里两个数都有，就都取自同一次运行 —— 因为它们要说的正是「第二张卡在两件事上值的钱不一样」，而把这两个数读自不同会话， 就等于把一条会话边界放进了比较本身。这也是那里的 A100 取 2026-08-30 而不是 08-29 的原因：早一场有解码，但它的 prefill 十一个档位里 0 个过闸 —— 当时开着 prefix caching，而这套阶梯每一档都是下一档的严格前缀，于是重复的那一轮什么都没算。

这是偏好，不是死规则。图 3 两边都用 2026-08-29 那场，因为只有那一场把两条投机臂互相测了； 而图 4 的 A100 prefill 按其性质就是一次补测 —— 第一遍根本没有产出能用的。 每个比较的每一侧都是一次运行；两侧不同天的地方，图上会写出来。 在这个模型上，两场 A100 在 2 K 以上吻合到 0.4 %，最浅的两档差 5.5 %。

31B 那一步的配置和以前一样：同一个 checkpoint gemma-4-31B-it-qat-w4a16-ct，batch 1， greedy，两个平台上注意力后端都是 TRITON_ATTN —— 这个模型 head 维度不齐，只要 FA4 不可用就会被强制走它，gfx1100 和 A100 都是这种情况。

两边都在自己的健康路径上，而这需要一个补丁 两列都让投机走 3D flash-decoding 路径，而原版 vLLM 在任一平台上都拒绝这么做 —— 那是另一篇文章的主题。 拿两边的原版配置去比，比的会是同一个 bug 的两个实例。这里用的机制是 vllm#45450 的， 以相同方式移植到两套栈上。

prefill 是拟合出来的，不是抄一个数。单独一个 prefill tok/s 什么都没说： S 个 token 的提示，首 token 时间走 T(S) = a + bS + cS²，而这篇文章比的两台机器在一项上差三倍、 在另一项上差近七倍。下面的拟合就是 `build_prefill.fits()` 的，和 prefill.jsonl --fits 报的是同一套，只在 chart-grade 档位上做。常数项 a 拟合了但从不引用： 同一条臂在两场 campaign 之间它从 9.8 ms 变成 99.8 ms，这套阶梯测不了它。

2一张卡对一张卡

先把张量并行完全拿掉：一张 7900 XT、一张 A100、一张 L4，同一套阶梯、同样两个模型。 A100 领先，幅度取决于模型，并且随深度收窄。L4 则根本没有领先。

L4 是一张在这件事上输给消费级卡的数据中心卡。两个模型、每一个深度上， 它都只有一张 7900 XT 的 0.54× 到 0.68×。它换来的是平坦 —— 32 K 上它保住 500-token 速率的 89 %， 而 A100 只保住 62 % —— 但那是一张显存慢的小卡的属性，不是优势。这张图该带走的一句是： 「数据中心」不是一个档次。而下一张图才是 L4 挣回位置的地方。

3第二张卡买到了什么

第二张 7900 XT 是图 1 里最平的那条线。稠密模型上跨十一个深度，它买到 1.13× 到 1.23×；MoE 上跨七个深度，1.11× 到 1.12×。 它甚至不是单调的：12B 上它先升到 6 000 token 处的 1.23×，再落到 32 K 的 1.13×。

原因是 batch 1 下一步解码既带宽受限又很短。把权重切开让每张卡少读一半字节，收益全在这里； 但此后每一步都以一次 all-reduce 收尾，而这笔开销不随切分变小，batch 1 下又只有一个 token 的工作量去摊它。第二张卡在带宽上贡献的，大半花在了线上。

prefill 是相反的情形，而且是同样两张卡。对提示做 attention 是按 head 并行的，完全不需要通信，而提示又长到让每步的固定开销变成舍入误差。 把两条臂都拟合出来、再在各自能到的最深档位上把两项加回去：稠密模型 32 K 上 40.1 秒变 21.5 秒，1.87×；MoE 12 K 上 6.21 秒变 3.99 秒， 1.56×。同样的硬件、同一天，收益是解码的四到七倍。

4prefill 是两项，而且两项不同向

线性项 b 是 GEMM 吞吐 —— 机器乘得多快。二次项 c 是 attention 随提示长度恶化得多快。一个 prefill tok/s 数字是这两项在某一个提示长度上的加权平均， 而权重随每一个提示长度改变。分开拟合之后，两项对同一对机器说的是不同的话：

稠密模型上，A100 在 attention 上的优势是它在算力上优势的两倍 —— 6.67× 对 3.29×。不管是什么在 prefill 上限制着 7900 XT，主要都不是乘法器。

MoE 上两者合并成一个数，5.71× 对 5.75×。这个模型每 token 只激活 26B 里的 4B，所以 GEMM 项在两台机器上都很小，两者之比也就不再是关于 GEMM 的了。

L4 在 b 上比消费级卡还慢，在 c 上好三倍。0.90× 与 3.01×。 这就是为什么它在 32 K 提示上比 7900 XT 快 1.58×，而在够短的提示上会输：两条曲线会相交， 「哪张卡 prefill 更快」是一个关于提示长度的问题。作为对照，第二张卡在 b 上买到 1.44–1.48×、 在 c 上买到 1.91–2.22× —— 二次项比线性项买得多，这和上面那两个墙钟数字说的是同一件事。

5两张卡对一张 A100

差距是平的，大约 1.4×。两边都是原版、两侧都不带补丁时，A100 在 500 档领先 1.36×，到 32K 是 1.44× —— 最窄在最浅的一档，最宽在最深的一档，跨越六十四倍的上下文范围。 这就是这篇文章原来那个标题所问问题的全部答案，也是仓库 README 发布的同一个比较。

那个领先，正是投机在 A100 身上的代价。投机只能从 2026-08-29 那一对上读， 因为只有那一场会话在两台机器上都跑了两条臂 —— 而它的 Radeon 一侧带着三个 A100 一侧没有的补丁， 所以它的绝对水平不如它的差值可信。不投机时那场会话给出的是 A100 领先 1.30× 到 1.46×，与上面那条原版阶梯接近。开了 MTP，这个领先就没了 —— 500 档 0.88×，2K 到 8K 持平，到 32K 也只有 1.08×。Radeon 并没有变快，是 A100 在投机上付出得更多。 而且不是因为它草稿猜得差：它的接受长度是两者中更好的那个，每步 1.92–2.07 对 1.46–1.53。 它亏在成本上 —— 一个投机步在它身上要花掉 2.40–2.57 个普通解码步，而同样一步在 Radeon 上只要 1.35–1.39 个。batch 1 下那对卡在一步之内有闲置算力，单卡没有，于是「多算三个 token 加跑一遍草稿模型」 这份固定开销，占它本来就在做的事情的比例大得多。两组数据在 benchmarks/campaign-2026-08-29/ 和 benchmarks/cuda-a100/campaign-2026-08-29/。

那个 U 是四个点。把探针打开，它确实在那儿 —— 1K 上 1.48×，到 16K 降到 1.14×，再回到 32K 的 1.87× —— 这篇文章就是为它取的名。而同一对机器、十一个对齐档位、每格两轮， 给出的是平的 1.36× 到 1.44×。那个看起来像谷底的 16K 点是一次运行的一个格子， 而它最深的邻居比的是两个不同的深度。这个形状没有在重测里活下来；它背后的数字仍留在页面上， 因为悄悄撤掉一张图比把它说过的话摆出来更糟。

现在 prefill 那一半也有了。直到 2026-08-30 之前，这个对比的 A100 一侧没有可用的 prefill：测它解码的那场开着 prefix caching，而这套阶梯每一档都是下一档的前缀， 于是重复的那一轮什么都没算，没有一档过得了重复性这一关。关掉缓存重测，覆盖这一对也跑的五个模型， 它说出了解码那一半没说的事：

算力项不在乎路径上是哪个 kernel，而 attention 项几乎就只是这件事。 五个模型上，A100 在 b 上领先 2.08× 到 4.00×，两个 kernel 分组的区间互相重叠。 到了 c 上两组根本挨不着：A100 与 Radeon 同在 Triton unified-attention 那一族的三个模型 是 2.99× 到 3.18×，而 A100 走 FlashAttention 的那两个是 12.75× 和 19.01×。

五个模型之间不同的不止是 kernel，所以那还只是相关。下面是同一台机器、同一天、同一个模型里的同一件事。 Qwen3.8-27B 在这两张卡上默认被路由到 ROCM_ATTN，可以用一个 flag 钉到 TRITON_ATTN。钉住之后它的 c 是 18.44 ns/token²，A100 领先 12.75×； 不动它，c 是 3.43，A100 领先 2.37×。一个 flag、没有补丁， 「A100 在长提示上领先多少」这个问题的答案挪了 5.38×。 这个 flag 正是这个仓库直到 2026-08-30 都称为「免费」的那一个；它在 32 K 上买到 1.15× 的解码， 卖掉的就是这个。

这些都不会让 A100 变慢。它在每个模型、两项上都领先。它们的意思是： 「数据中心卡快多少」这个单一数字并不是两张卡的属性 —— 在二次项上它大部分是 「两边各自落到了哪个 attention kernel」的属性，而在这套硬件上，那由一张路由表和一个命令行 flag 决定。

6付代价的是切分，不是硅片

7它同样侵蚀投机

MTP 草稿模型只有四层深，所以多出来的那次前向很便宜。不便宜的是：每一次草稿步仍然是一步， 而 TP=2 下的一步无论挂着多大的模型，都要付那个 all-reduce 下限。 这个下限不随草稿模型变小，所以让投机划算的那笔账，在两张卡上比在一张卡上更难算平。

9没有被确立的部分

批量吞吐，以及 prefill 的常数项

这里的一切都是 batch 1。批量吞吐是另一个 regime，完全没有测；一旦解码不再是带宽受限的， 第二张卡那个 1.1× 就没有理由继续成立，这一页上别的东西也一样。prefill 确实测了， 但只测了它的两个形状项：常数 a 拟合了却从不引用，因为同一条臂在相隔一个月的两场 campaign 之间它从 9.8 ms 变成 99.8 ms，另一条臂上它还出来过负值。所以够短的提示落在这些拟合 描述的范围之外。

单卡上的 gemma-4-31B

31B 没有单卡这一行，在这台机器上也不可能有 —— 22 GB 的权重，20 GB 的卡。 所以前两步由另外两个模型承担，31B 从第三步起才出现 —— 在那里，这一对卡本来就是这台机器跑得动它的唯一方式。

A100 自己的实到带宽

图 7 只有 Radeon 这边，没有对应的一半。图 3 里那个 1.27× 是两个规格书数字的比值， 读者应当把它当成"单靠带宽差能解释的上界"，而不是任何一侧被拿去对照过的预测。

每边一套栈，每种卡各一张

两个不同的 vLLM 版本，因为每一侧跑的都是它今天真正在跑的那套； 不同的运行环境，其中两个是租来的 Colab VM，会话之间的方差没有量化。 而且 A100 和 L4 各只有一张、各只测过一次：这里没有任何东西能把一款卡和这一张卡分开。

投机那一对没有做到补丁对齐

图 3 的实线两侧都是原版、都不带补丁，所以由它承担这个比较。画在它下面的 2026-08-29 那一对 不是：它的 Radeon 臂跑着 vllm#45916、window block-skip 和 vllm#45450，而 A100 臂在不投机时一个都没有、投机时也只有 vllm#45450。没有任何一场不带补丁的会话同时跑过两条投机臂， 所以「投机对每台机器要价多少」要么从那一对上读，要么读不到 —— 被主张的是它两条臂之间的差值， 不是任一条臂所处的水平。投机本身倒是对齐的：两份 serve 日志都记录了 SpeculativeConfig(method='mtp', …, num_spec_tokens=3)，指向同一个 assistant checkpoint， 这一点由 verify_doc_figures.py 从日志里断言。

第二张卡为什么是这个表现

「batch 1 下一步解码短到让一次固定的 all-reduce 吃掉第二张卡大半带宽，而 attention 的并行不需要它」——这个说法和这一页上每一个测量都一致，但没有任何一个测量证明它。 这里没有给任何一次 all-reduce 计过时。三条曾经试图给那个下限一个数字的已发表结论， 已在 2026-08-30 撤回，因为它们所依赖的那一项这套阶梯测不了。
