两张 Radeon 上的解码速率与预填充扩展；对照单卡、A100 和 L4 实测

对本文比较的两个模型，增加第二张 RX 7900 XT 后，batch-1 解码速率为单卡的 1.11× 到 1.23×。预填充的收益更大：32 K 提示的处理时间从 40.1 秒降到 21.5 秒，加速比为 1.87×。两组测试使用同样的显卡，在同一天完成；第二张卡对解码和预填充的帮助不同。

__CHIPS__

摘要

这组比较分为三个问题：单张 RX 7900 XT 与单张数据中心 GPU 的性能差多少，增加第二张 Radeon 有多少收益，以及双卡与单张 A100 的差距。单卡测量为前两项比较提供基线。

这两个模型的解码收益有限。增加第二张卡后的解码加速比为 1.11× 到 1.23×。实测 all-reduce 约占单步时间的九分之一，无法解释大部分未达到理想加速比的差距。同一台机器上的 Qwen3-8B 在通信开销相近时达到 1.70×，第 9 节分析了这一差异。按实际耗时计算，预填充加速比为 1.56× 到 1.87×；其中的注意力计算可以按 head 分配，不需要集合通信。

预填充的线性项与二次项扩展程度不同。按 T(S) = a + bS + cS² 拟合，在稠密 12B 上，A100 相对单张 7900 XT 的速率比为 b 项 3.3×、c 项 6.7×。在 4B 激活参数的 MoE 模型上，两项较为接近，分别是 5.75× 和 5.71×。L4 的 b 项为 Radeon 的 0.90×，c 项为 3.0×。用一个预填充加速比无法表达这些差别。

第三项比较是两张 Radeon 与单张 A100。不启用投机解码时，2026-08-29 的配置在十一个上下文长度上测得 A100 领先 1.30× 到 1.46×。这组配置的补丁没有完全对齐，图 3 将其与原版对照区分展示。完整测试没有复现最初四个单次测量点所暗示的 U 形差距。

1比的是什么

共有四种机器配置参与比较：单张 RX 7900 XT、两张 RX 7900 XT，TP=2、单张 A100-SXM4-80GB 以及单张 L4。受限于三种硬件架构，并非每个模型都能在所有机器上运行；其中两处缺少数据是因为显存容量不足。gemma-4-26B-A4B 在单张 7900 XT 上只测到 12 000 token：在 19.98 GiB 的显卡上驻留 16.96 GiB 权重后，即便显存利用率设为 0.95，也仅剩下 0.93 GiB 用于 KV 缓存，而扩展到 32 K 则需要大约 0.97。此外，gemma-4-31B-it 完全没有单卡数据行，因为 22 GB 的权重无法装入 20 GB 的显卡，双卡是这台机器运行该模型的唯一方式。31B 只用于第三项比较。

解码与 prefill 的来源 只要条件允许，前三步的解码与 prefill 数据均取自同一轮会话。本比较的主张在于第二张卡在两种任务下的行为截然不同，混用不同会话的数据会引入跨次运行的方差。基于这一要求，A100 数据采用了 2026-08-30 的会话，而非 2026-08-29：早先那一轮虽包含解码数据，但在开启 prefix caching 的情况下，prefill 阶梯的 11 个档位中有 0 个达到图表入库标准。由于阶梯中的每一档都是下一档的严格前缀，启用缓存导致重复 token 的开销被完全抹平。

这种一致性属于优先策略而非绝对规则。图 3 对两个平台均采用 2026-08-29 的数据，因为只有该轮测试直接比对了两种投机配置。图 4 中 A100 的 prefill 数据在结构上属于后续补测，首次测试未能产生可用的有效数据。每一项比较的两侧各代表一次单轮运行；当两侧数据采自不同日期时，图表会明确标注差异。在 2 K 以上的深度，两轮 A100 测试在该模型上的吻合度达到 0.4 %，最浅的两档差异为 5.5 %。

31B 这一步保持了原始配置：使用 checkpoint gemma-4-31B-it-qat-w4a16-ct、batch 1 以及 greedy 采样。两个平台均在 TRITON_ATTN 注意力后端上运行。该模型不规则的 head 维度导致在 FA4 不可用时只能强制退回 Triton，无论对 gfx1100 还是 A100 均是如此。

两套栈都需要补丁才能使用 3D 投机解码 两列配置均将投机解码路由至 3D flash-decoding 路径。原版 vLLM 在两个平台上均会在投机时禁用该路径，具体分析见另一篇文章。直接对比原版配置无非是比对同一个缺陷的两个实例。该修复将 vllm#45450 的机制以完全相同的方式移植到了两套软件栈上。

预填充按多个上下文长度进行拟合。单个吞吐值无法描述非线性的变化。这里使用 build_prefill.fits()，在符合绘图筛选条件的测试点上拟合首 token 时间 T(S) = a + bS + cS²，与 prefill.jsonl --fits 使用同一函数。常数项 a 参与拟合，但不用于比较：同一配置在两批测试间从 9.8 ms 变到 99.8 ms。

2一张卡对一张卡

先剥离张量并行：在单张 7900 XT、单张 A100 与单张 L4 上，使用相同的阶梯测试两个模型。A100 全程保持领先，领先幅度因模型而异，并随上下文深度增加而收窄。L4 则全程落后。

L4 在这组测试中的解码速率较低。在两个模型和所有测过的上下文长度下，它的速率为单张 7900 XT 的 0.54× 到 0.68×。到 32 K 时，它保留了 500-token 速率的 89 %，A100 则保留 62 %。保留率较高不等于绝对吞吐更高。下文的预填充测试比较的是另一部分工作负载。

3从单卡到双卡的加速比

第二张 7900 XT 构成了图 1 中最为平缓的曲线。在稠密模型的十一个深度上，它仅带来 1.13× 到 1.23× 的收益；而在混合专家模型的七个深度上，收益仅为 1.11× 到 1.12×。这种扩展甚至不是单调的：在 12B 模型上，加速比在 6 000 token 处达到 1.23× 的峰值，随后在 32 K 下滑落至 1.13×。

切分模型权重能减少每张 GPU 需要读取的字节数，但集合通信仍会增加延迟。本页此前假设解码受显存带宽限制，并将大部分未实现的加速归因于通信。直接计时不支持这一解释：通信约占单步时间的九分之一，即 12B 每步 16.70 ms 中的 1.85 ms。同一台机器上的另一个模型在通信开销相近时达到 1.70×。第 9 节对照了实测的内存控制器忙碌比例。

同样两张卡在预填充上的收益更大。提示阶段的注意力计算跨 head 并行且完全无须通信，较长的提示也降低了固定开销占总时间的比例。对两组测试配置进行拟合，并在各自达到的最深档位上合并各项：在稠密模型上，32 K 时用时由 40.1 秒缩减至 21.5 秒，收益为 1.87×；在混合专家模型上，12 K 时用时由 6.21 秒缩减至 3.99 秒，收益为 1.56×。同样的硬件与同一天的测试，增益却达到了解码阶段的四到七倍。

在稠密模型上，A100 的注意力优势相当于其算力优势的两倍：6.67× 对比 3.29×。无论 7900 XT 在 prefill 阶段的主要瓶颈是什么，乘法器本身都不是核心原因。

在混合专家模型上，两个差距重合在一起，分别为 5.71× 与 5.75×。该模型每个 token 仅激活其 26B 参数中的 4B，导致 GEMM 项在两台机器上均维持在极低水平，两者之间的比值已无法反映矩阵乘法的吞吐差异。

L4 在 b 项上慢于消费级卡，在 c 项上则领先三倍。实测表现为 0.90× 与 3.01×。这解释了为何它在 32 K 提示上比 7900 XT 快 1.58× 却在短提示下落后：两条性能曲线发生交叉，使得 prefill 的优劣完全取决于提示长度。相比之下，第二张卡在 b 项上带来 1.44–1.48× 的提升，在 c 项上带来 1.91–2.22× 的提升，对二次项的改善幅度高于线性项，与前文测得的实际耗时一致。

5两张卡对一张 A100

性能差距平稳保持在约 1.4×。两端均运行未经修改的原版代码且不带补丁时，A100 在 500 档领先 1.36×，到 32K 是 1.44×。在十一个对齐的深度档位上，这一差距全程保持平缓。早先测得的 U 形曲线是缺乏对照的四个离散点造成的假象；当前数据每个测试点均取两轮均值，证实差距全程平稳。

这一领先幅度反映了投机解码给 A100 带来的代价。投机解码必须基于 2026-08-29 的测试组进行评估，因为只有该会话同时在两台机器上运行了两种测试配置。同时其 Radeon 一端应用了三个 A100 一侧没有的补丁，因此其相对差值比基准水平更具参考价值。在未启用投机时，该会话显示 A100 领先 1.30× 到 1.46×，接近上文的原版阶梯。开启 MTP 后领先优势消失：500 档仅为 0.88×，2K 至 8K 区间持平，到 32K 也仅有 1.08×。这并非因为 Radeon 变快，而是 A100 在投机解码上付出了更高代价。原因也不在于草稿质量：它的接受长度实际上是两者中更好的一方，单步达到 1.92–2.07 个 token，而 Radeon 为 1.46–1.53。它亏在成本上：在它上面单次投机步耗时相当于普通解码步的 2.40–2.57×，而同样一步在 Radeon 上仅需 1.35–1.39×。在 batch 1 下，双卡组合在单步内存在充裕的闲置算力，而单卡缺乏这种算力余量，使得生成并验证四个 token 的固定开销在既有负载中所占比例高得多。两项数据分别位于 benchmarks/campaign-2026-08-29/ 与 benchmarks/cuda-a100/campaign-2026-08-29/。

所谓的 U 形曲线仅由四个数据点构成。开启探针后该曲线确实呈现：1 K 时为 1.48×，在 16 K 时降至 1.14×，随后在 32 K 回升至 1.87×，正是这些数值构成了本文的原标题。然而同样的测试在两台机器上按每个测试点两轮取均值后，呈现出的却是一条 1.36× 到 1.44× 的平直走势。早先看似极小值的 16 K 点不过是单次运行中的孤立测试点，而且最深的测量点比较的是两个不同的上下文长度。该形态未能在复现测试中维持；原始数据点仍保留在页面上。

prefill 维度的实测数据现已补齐。在 2026-08-30 之前，该对比中 A100 一侧始终缺乏有效的 prefill 数据：早先测量解码的会话开启了 prefix caching，而测试阶梯的每个档位均为下一档的前缀，导致重复 token 被错误计为零开销从而未能满足可重复性标准。在关闭缓存并在两个系统上针对五个模型重新测量后，prefill 揭示了解码过程中无法观察到的运行动态：

算力项并不关心执行路径上使用的是哪种 kernel，而注意力项几乎完全取决于此。在全部五个模型上，A100 在 b 项上领先 1.92× 到 4.00×，不同 kernel 实现之间的分布区间彼此重叠。但在 c 项上，两者完全分化：在 A100 与 Radeon 同样采用 Triton unified-attention 家族的三个模型上，领先优势为 2.99× 到 3.10×；而在它通过 FlashAttention 提供服务的两个模型上，优势跃升至 11.94× 和 19.01×。

五个模型之间的差异不仅限于 kernel，因此前述表现仅属于相关性。而在同一台机器、同一天及同一个模型内部，这一效应得到了直接验证。在这组显卡上，Qwen3.8-27B 默认被路由至 ROCM_ATTN，但可以通过指定 flag 固定为 TRITON_ATTN。在固定后端后，其 c 项耗时为 17.27 ns/token²，A100 领先 11.94×；保持默认时，其 c 项为 4.46，A100 领先 3.08×。仅需一个 flag 且无须任何补丁，「A100 在长提示词上领先多少」的答案便发生了 3.87× 的转移。该 flag 直到 2026-08-30 之前一直被本仓库视作「零代价」；它在 32 K 深度换取了 1.15× 的解码增益，却付出了如此代价。

这丝毫没有削弱 A100 的地位：它在每个模型及两项指标上均保持领先。但这表明，关于「数据中心卡到底快多少」的单一数字并不是这两张卡本身的属性：在二次项上，它主要取决于两端各自最终采用了哪种注意力 kernel，而在当前硬件配置下，这由一张路由表和一个命令行 flag 决定。

6付代价的是切分，不是硅片

原版 vLLM 在投机解码时陷入的 2D 注意力路径，会为每个 KV head 启动一个 workgroup。当前模型包含 16 个 head。单卡上单个 rank 可以处理全部 head；而在双卡切分下，每个 rank 仅分到八个。本就饥饿的执行路径因并行切分而遭受加倍的饥饿，这直接体现在保留率数据中：

7投机解码中的集合通信开销

MTP 草稿模型只有四层，前向计算量较小，但 TP=2 下每个草稿步骤仍需承担集合通信延迟。31B 的实测基线为每步 2.30 ms，不随草稿模型深度改变。这会降低双卡相对单卡的投机解码收益。

9没有被确立的部分

批量吞吐，以及 prefill 的常数项

基准测试全部在 batch 1 下运行。未进行实测的批量吞吐属于另一个工作区间；一旦解码脱离显存带宽受限状态，第二张卡的 1.1× 提升及本页其他结论均不再适用。prefill 虽然经过实测，但仅覆盖两个形状项：常数项 a 虽经拟合但从不引用，因其在相隔一个月的两场 campaign 中于同一配置下从 9.8 ms 漂移至 99.8 ms，在另一配置下甚至出现负值。因此足够短的提示超出了当前拟合所能描述的范围。

单卡上的 gemma-4-31B

31B 在当前机器上缺失且无法获得单卡数据：模型权重为 22 GB，而显存仅有 20 GB。分析的前两步依赖其余模型完成，31B 仅在必须双卡运行的第三步介入。

A100 自己的推得带宽

图 7 仅展示 Radeon 平台，对应另一平台的数据未做实测。图 3 标注的 1.27× 仅为官方标称规格的比值，代表纯带宽差异所能解释的性能上限，而非任何一方经过实测对照的理论预测。

每边一套栈，每种卡各一张

两端各自运行原生软件栈的不同 vLLM 版本，且测试跨越了会话方差未量化的租赁 Colab 虚拟机。测试中 A100 与 L4 均仅使用单张显卡完成单次测量，无法将芯片架构特性与特定硬件实例的影响剥离开来。

投机那一对没有做到补丁对齐

图 3 的实线基于两端未经修改的原版代码展开对比。2026-08-29 的测试组未做补丁对齐：Radeon 端运行了 vllm#45916、window block-skip 与 vllm#45450；而 A100 非投机端省略了全部三个补丁，投机端仅运行 vllm#45450。在缺乏同时覆盖两组配置的原版测试情况下，MTP 开销必须从相对差值而非绝对水平中解读。投机配置本身完全对齐：由 verify_doc_figures.py 断言，两端 serve 日志均记录了指向相同 assistant checkpoint 的 SpeculativeConfig(method='mtp', …, num_spec_tokens=3)。

第二张卡为什么是这个表现

本页原先说：batch 1 单步解码时间极短，固定的 all-reduce 延迟吞噬了第二张卡贡献的大半带宽，而且这里没有给任何一次 all-reduce 计过时。现在完成实测后，数据并不支持这一判断。在 HIP graph 回放模式下（serve 日志记录为 cudagraph_mode FULL_AND_PIECEWISE 与 Capturing CUDA graphs (decode, FULL)，即解码真正运行的机制），batch 1 形状下一次 all-reduce 是 16.6 到 21.5 µs。按 2 × 层数 + 1 次集合通信计算（于 2026-09-03 清点：每层两次加一次 embedding），通信耗时仅占 12B 一步 16.70 ms 里的 1.85 ms，约九分之一。

而且同一台机器上，Qwen3-8B 的第二张卡在解码上值 1.70×， 12B 只值 1.185×，两者单步集合通信开销相差在 0.6 ms 以内。若通信线路吞噬了带宽，8B 便无法达到 1.70×。仅靠通信无法解释 12B 的扩展收益。减去理想减半耗时与实测集合通信开销，12B 还剩 4.96 ms 无法解释，8B 只剩 0.66 ms。（2026-09-02 得出解答：此前的假设存在缺陷。）原先的分析假设显存带宽构成瓶颈；然而在单卡上 8B 让内存控制器达到 90 % 忙碌，而 12B 仅有 56 %。五个测试点的扩展收益排序与内存控制器忙碌比例一致（campaign-2026-09-02d）。12B 剩余的 4.96 ms 说明：内存控制器未充分忙碌时，理想减半模型不能准确估计双卡耗时。该计数器此后在四种租赁 NVIDIA 配置下成功对高带宽显存、双卡扩展以及降级显卡的价值做出了排序，相关分析见独立专文。

关于注意力并行的观察仍然成立：注意力计算在无须通信的前提下实现并行，上述 prefill 数据充分证实了这一点。而此前依据拟合截距对集合通信进行定量评估的三项结论依然处于撤回状态：相关量在当前阶梯上无法定量，且被小 49 到 63 倍的直接实测数据所推翻。实测数据已在仓库中归档，运行时库由 /proc/self/maps 直接读取确定而非依据版本常量。
