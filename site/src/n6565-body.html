An upstream issue reports deterministic silent corruption during a collective on two gfx1100 cards. On this pair of gfx1100 cards, the corruption does not appear. That clean run proves almost nothing on its own. It gains value only through three concrete checks that do not depend on running the test more times.

Abstract

Issue ROCm#6565 reports that all_gather silently returns corrupted data on two W7800s. The upstream report traces the fault to an init-time 8-byte copy whose payload is missing from device memory when synchronisation returns. It reproduces deterministically for them on RCCL 2.27.7 and 2.28.3. On this box running 2.30.4, no corruption appears across 135 cold communicator initialisations in eight configurations.

Three things make that negative result informative. First, a sweep across the dimensions their mechanism names. The reported fault affects only the first of several concurrent init copies. Because this host initialises two channels by default, the sweep scales channel count from one to sixteen and switches the transport from shared memory to sockets. Second, a stated contrast between the two testbeds. The machines differ in platform, kernel, and RCCL version, but agree on PCIe atomics and IOMMU, so the obvious explanations are named rather than left for the reader to guess at. Third, an honest bound on what a clean run from someone else's script can say.

That third one turned out to be the interesting one. The upstream reproducer computes corruption checks across all ranks but tallies failures only on rank 0; consequently, corruption visible only on rank 1 would print ALL CORRECT. The negative result was therefore narrower than originally reported. That limitation was disclosed the same night. A cross-rank variant was then written, and all eight arms were re-run through it. Finally, rather than merely debating the script logic, the blind spot was demonstrated on this hardware by injecting a one-sided fault.

1Why a clean run usually says nothing

"It works here" is the least useful sentence on a bug tracker. It can mean the reporter is mistaken, the reporter ran a configuration omitted here, or the test harness cannot observe the failure mode. Turning a negative result into actionable evidence requires answering three questions before posting: could this configuration trigger the bug, what differs between the two machines, and what blind spots exist in the test tool.

This first question makes the parameter sweep essential. The failure mechanism is specific rather than generic: the first-issued copy on channel 0 fails on both ranks, whereas the copy on channel 1 lands. The reporter found that a single-device allocate → memset → 8-byte async copy → synchronise → read loop never reproduced the fault in 200 tries. Concurrent multi-device initialisation is therefore a necessary ingredient. A benchmark that never issues concurrent initialisation copies tests nothing relevant.

The channel sweep gives the negative result its evidentiary weight. By default, this host initialises two channels, matching the exact topology where the first copy fails while the second lands. Forcing one, four, eight, and sixteen channels alters the number of concurrent initialisation copies, while disabling shared memory forces transport across sockets. Across all configurations, execution remains completely clean.

2What differs, stated rather than left to the reader

A negative result isolates one specific cell within a larger parameter space. Its utility depends entirely on identifying that cell with precision. Attributes that agree between systems matter as much as those that differ: if this host lacked PCIe atomics or ran without an IOMMU, maintainers could dismiss the observation immediately.

3The bound, and then the demonstration

The initial sweep executed the reporter's script verbatim from the issue tracker, without retyping, citing its md5 checksum for independent verification. Running the unmodified upstream script made the negative result credible, but it also imported the script's hidden defect.

rccl_allgather_truth.py · the shape of it
bad_list = [...]        # computed on every rank
bad_into = [...]        # computed on every rank
if rank == 0:           # and only rank 0 counts, or prints
    if bad_list or bad_into:
        fail += 1

When corruption occurs exclusively on rank 1, the script detects the bad data but discards the result, reporting ALL CORRECT regardless. Since every pass among the 135 runs relied on that tally, the negative result established only that there was "no corruption observed on rank 0". That limitation was documented in the repository ten hours after the upstream comment was posted, prior to any public inquiry.

Modifying the reporter's script directly was not an acceptable fix. Altering the script, even to insert a cross-rank reduction, destroys its status as an impartial test. The original file was therefore preserved alongside its cryptographic hash, an independent variant was implemented, and both were evaluated in parallel.

The variant was then evaluated across the identical eight arms and sample sizes, recording 135 of 135 clean executions verified across both ranks. Rather than refining a caveat, the new benchmark replaces uncertainty with verified data. Both sweeps are validated to ensure they cover the same configurations at matching sample counts, preventing any silent divergence.

The check that miscounted, and why it is here The initial harness counted reporting ranks using grep -c, which tallies lines rather than occurrences. Because both ranks frequently write output on a single line, the harness misreported 6 of 20 runs as one-sided when both ranks had in fact reported. No measurement was compromised—since the script performs an internal all-reduce—but this mirrors the exact failure mode under investigation. A check that miscounts is worse than no check. Counting token occurrences resolved the error.

4The witness that did not come up

The verification plan included a second witness that bypassed PyTorch by employing the reporter's alternative reproducer. The rccl-tests suite compiled cleanly against the container toolchain, producing confirmed gfx1100 code objects for both benchmark and verification binaries. However, both logged all_gather runs aborted on rank 1 inside the data-initialisation kernel with HIP failure: 'invalid device function'. The abort occurs identically whether the verification pass is enabled or disabled, clearing the verification kernels of blame. Subsequent arms in the test script never executed, and the test tree remained on a deprecated branch against RCCL 2.30.4.

Rather than discarding this abort, the raw unfiltered log was committed to record the constraint. An earlier run used a wrapper to parse console output, but its regex matched nothing, producing spurious FAILED verdicts for every collective—including workloads that the PyTorch harness passed 135 times over. That corrupted log was deliberately discarded—because a wrong verdict line is worse to leave lying around than no log—and the raw execution trace replaced it.

5What is not established

Version against platform

This host differs on RCCL version and platform, so a clean run isolates neither factor. Two tests would separate them, but neither is cheap here. The reporter can test 2.30.4 in minutes from source. Deploying 2.28.3 here requires a 73 GB image against 40 GB free, destroying active container state. Both missing runs are documented in source so successors need not rediscover them.

What 135 cold inits bounds

The clean run bounds the defect as not universal to gfx1100 under RCCL, and absent at 2.30.4 on this host across all tested channels and transports. It sets no bound on the reporter's own configuration at all, and it cannot: their failure is deterministic on their machine.

The second witness

Only one reproducer ran. It is the reporter's own primary one, which is the right one to have; an independent second path would have been better, and the rccl-tests attempt did not produce one here.
