How to report a bug you cannot reproduce

Someone reports deterministic silent corruption in a collective on two gfx1100 cards. You have two gfx1100 cards. It does not happen. That is worth almost nothing on its own — and it can be made worth something, by three things that have nothing to do with running the test more times.

__CHIPS__

Abstract

ROCm#6565 reports all_gather silently returning wrong data on two W7800s, root-caused to an init-time 8-byte copy whose payload is not in device memory when the synchronise returns. It reproduces deterministically for them on RCCL 2.27.7 and 2.28.3. On this box at 2.30.4 it does not, across 135 cold communicator initialisations in eight configurations.

Three things make that mean something. A sweep across the dimensions their mechanism names: their mechanism is specific to the first of several concurrent init copies, this box builds two channels by default, and the sweep drives that from one to sixteen and the transport from shared memory to sockets. A stated contrast: the two machines differ on platform, kernel and RCCL version, but agree on PCIe atomics and IOMMU, so the obvious explanations are named rather than left for the reader to guess at. And an honest bound on what a clean run from someone else's script can say.

The third turned out to be the interesting one. Their reproducer computes the corruption check on every rank but counts failures only on rank 0, so corruption visible only on rank 1 would print ALL CORRECT. The negative result was therefore narrower than it had been reported as. That was disclosed the same night, a cross-rank variant was written, all eight arms were re-run through it, and the blind spot was demonstrated on this hardware by injecting a one-sided fault rather than argued from the source.

1Why a clean run usually says nothing

"It works here" is the least useful sentence on a bug tracker. It is compatible with the reporter being wrong, with the reporter being right about a configuration you did not run, and with your test being unable to see the fault at all. Turning it into something a maintainer can act on means answering three questions before pressing send: could this configuration have shown it, what exactly differs between the two machines, and what is the instrument blind to.

The first is why the sweep is the load-bearing part. Their mechanism is not "collectives are broken": the first-issued copy, on channel 0, is the one lost, on both ranks, while channel 1's lands. They report that a naive single-device version of the same allocate → memset → 8-byte async copy → synchronise → read sequence does not reproduce in 200 tries. So the concurrent multi-device init pattern is a necessary ingredient, and a run that never has several concurrent init copies is not a test of anything.

The channel sweep is what makes the negative admissible. This box builds two channels by default, which is exactly the shape their first-loses-second-lands observation needs; forcing one, four, eight and sixteen changes the number of concurrent init copies, and disabling shared memory moves the transport onto sockets. All of it stays correct.

2What differs, stated rather than left to the reader

A negative result is a claim about a cell in a space, and it is only useful if you say which cell. The rows that agree matter as much as the ones that differ: if this box were atomics-starved, or had no IOMMU where they had one, a maintainer could discount the whole thing in one line.

3The bound, and then the demonstration

The first sweep used the reporter's script exactly as published — extracted from the issue body, not retyped, with its md5 quoted so anyone can confirm it. That is the property that makes a negative from it worth anything to them, and it is also what carried the defect in.

rccl_allgather_truth.py · the shape of it
bad_list = [...]        # computed on every rank
bad_into = [...]        # computed on every rank
if rank == 0:           # and only rank 0 counts, or prints
    if bad_list or bad_into:
        fail += 1

Corruption visible solely on rank 1 is computed, then discarded, and the run still prints ALL CORRECT. Since every one of the 135 passes was that script's verdict, the negative result was really "no corruption observed on rank 0". That gap was written into the repository ten hours after the comment went out, before anyone asked.

The fix is not to edit their script. Editing it, even to add a reduction, costs the one property that makes the result credible to them. So the original stays untouched and hashed, a variant was written alongside it, and both were run.

Then the same eight arms at the same counts, through the variant: 135 of 135 again, correct on both ranks. The caveat is not restated more carefully — it is replaced by a result. And the two sweeps are checked to cover the same arms at the same counts, because a re-run over a different set would not replace anything.

The check that miscounted, and why it is here The first version of the arm runner counted reporting ranks with grep -c, which counts lines. The two ranks frequently print on one line, so it reported 6 of 20 runs as one-sided when both ranks had in fact reported. No measurement was affected, because the verdict is all-reduced inside the script itself — but this is the same class of mistake as the one the whole stage exists to fix, and a check that miscounts is worse than no check. Counting occurrences instead fixed it.

4The witness that did not come up

The plan had a second witness that does not go through PyTorch, using the reporter's other reproducer. rccl-tests builds cleanly against this container's toolchain, with gfx1100 code objects confirmed in both the benchmark and the verification object, and then both of the logged all_gather runs abort on rank 1 at the data-initialisation kernel with HIP failure: 'invalid device function'. It fails identically with and without the verification pass, so it is not the verification kernels; the script's later arms never ran; and the clone is on the deprecated branch against RCCL 2.30.4.

That is recorded as a limitation rather than dropped, and the unfiltered log is what is committed. An earlier attempt ran through a wrapper that parsed the output; the filter matched nothing and printed FAILED for every collective including one the PyTorch test passes 135 times over. That log is deliberately not kept — a wrong verdict line is worse to leave lying around than no log — and the raw re-run replaced it.

5What is not established

Version against platform

This box differs from theirs on RCCL version and on platform, so a clean run here does not say which axis matters. Two runs would separate them and neither is ours to do cheaply. The reporter running 2.30.4 on their box is minutes for them, since they already build from source; this box running 2.28.3 needs a 73 GB image against 40 GB free and would destroy container state in use for other work. Both are named in the source so the next person does not have to rediscover them.

What 135 cold inits bounds

It bounds the defect as not universal to gfx1100 plus RCCL, and as not appearing at 2.30.4 on this hardware under any transport or channel count tried. It does not bound the reporter's own configuration at all, and it cannot: their failure is deterministic on their machine.

The second witness

Only one reproducer ran. It is the reporter's own primary one, which is the right one to have, but a second independent path would have been better and did not build usefully here.
