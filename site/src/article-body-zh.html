12.1 到 4.2 tok/s：
解码耗时主要增加在 Triton paged attention

vLLM 下双卡 Radeon 上的混合 SSM 解码速率；以稠密模型、llama.cpp 与上游 split-KV 内核作对照检验

线性注意力本应让长上下文的处理开销变低。在这台机器上，Qwen3.6-27B 在 500 到 32 000 token 之间从 12.1 跌落至 4.2 tok/s；而同一天下午测得的稠密 8B 模型仍保持了 77 % 的短上下文速率。问题并不出在 48 层线性注意力上，而是剩下的 16 层。

__CHIPS__

摘要

在 vLLM 下，一个混合 Mamba / gated-delta-net 架构的 checkpoint 在 500 到 32 000 token 上下文之间失去了 65 % 的解码速率。这条下滑曲线比同一台机器、同一场 campaign 中测得的任何稠密模型都要陡十四到四十倍。

内核级 profile 显示，新增耗时主要来自 kernel_paged_attention_2d，即模型 16 层全注意力使用的 Triton 回退实现。其单次调用耗时变为短上下文时的 28.3 倍，其余内核耗时基本不变或略有下降。线性注意力层在这组测量中没有变慢。

该模型不满足 ROCm 自定义 paged-attention 内核的三个启用条件，因此使用 Triton 回退实现。在 batch 1、4 个 KV head 的配置下，该实现可利用的并行度较低。单卡功耗随上下文增长而下降，且每读取一个 KV 字节的耗时远高于稠密对照模型，这两项观察支持占用率不足的解释。

同一台机器、同一天的 llama.cpp 对照中，同一 checkpoint 家族的斜率低了 28 倍。这支持问题主要出在具体实现，而非硬件整体限制的判断，但两个引擎使用的量化格式不同。上游 split-KV 补丁在下文测试了两次，最近一次是 vLLM 0.27 上的受控 A/B：32 K 上下文下加速 9.46 倍。其中一个测试点呈双峰分布，下文保留了相应说明。

1测了什么，怎么测的

第 2 节使用同一天下午、同一套软件栈上的一批测试数据，包含五种架构、十一个上下文长度，共 292 次解码和预填充测量。测试使用 vllm serve、TP=2、CUDA graph、--gpu-memory-utilization 0.85 和 512 token 输出，结果取两轮均值。

每个测试点只有二到四轮测量。这里报告极差占均值的百分比，用于展示实际观察到的轮次间波动，而不将其视为对总体变异程度的精确估计。将光标悬停在图 1 的数据点上，可查看轮数和极差。

关于绝对数值的解读 测试运行在 VFIO 虚拟机中，GPU 之间没有 P2P，使用跨 die 的 PCIe 3.0 链路。速率和曲线形态都只描述这组配置，尚未证明能推广到其他拓扑或软件栈。

2观察到的现象

在十一个上下文长度上，五种架构中的四种只有较缓的解码速率下降，混合模型的下降则明显更大。

混合模型在所有测试长度下的解码速率都最低，仅凭参数量无法解释这个结果。它的曲线向下弯曲也最明显。到 32 000 token 时，其他配置保留了短上下文速率的 67 % 至 78 %，该模型为 35.1 %。

若折算为斜率（即每增加一个 token 上下文所带来的解码微秒增量），本场 campaign 中混合模型的值为 4.84 µs，而稠密 8B 对照模型仅为 0.118 µs。二者相差约 41 倍。下面检查这部分差距来自哪些内核。

3从内核 profile 定位新增耗时

在两个上下文深度下进行的 torch profile 均保持开启 CUDA graph。我们将内核调用严格归属到其所对应的引擎步时间窗口内，从而避免将分块预填充（chunked prefill）的调用混入解码数据中。

48 个 gated-delta-net 层在 32 K 处的耗时是 1 K 处的 0.95 倍，量化 GEMM 的耗时也基本不变。只有 paged-attention 内核明显变慢，耗时达到短上下文时的 28.3 倍。

按每步调用 16 次计算，paged attention 的耗时从每步 5.71 ms 增至 161.5 ms，增加 155.8 ms。CUDA graph 回放测得的整个解码步骤从 85.85 ms 增至 236.9 ms，增加 151 ms。两项增量接近，说明新增解码耗时主要来自 paged attention。其他内核在较长上下文下耗时基本不变或略有下降。

4为什么会走回退路径

模型不满足自定义内核的启用条件，因此 16 层全注意力使用 Triton。在 vllm/platforms/rocm.py 的 use_rocm_custom_paged_attention 中，RDNA 分支除其他条件外，还要求 head_size == 128 和 block_size == 16。

use_rocm_custom_paged_attention · 反事实调用
# 在运行中的引擎上测出来的，不是从 config 里读的
head_dim                = 256       # gate 要 128
cache_config.block_size = 784       # = 16 x 49，gate 要 16
is_pow2(784)            = False     # 在它自己那条路径上就否掉 use_custom
gqa_ratio               = 6         # 这一条是过的

# 单独放宽任何一个不满足的条件，仍然不够
use_rocm_custom_paged_attention(head_size=128)   -> False
use_rocm_custom_paged_attention(block_size=16)   -> False

单独放宽一个不满足的条件，仍无法启用自定义内核。chunked_prefill_paged_decode.py 还会因独立的 is_pow2 检查不通过而禁用 use_custom。对当前实现而言，优化回退内核可以在不扩展自定义内核支持范围的情况下加速该模型。

仅放宽选择条件还不够 仅放宽 head_size 检查只是将报错位置转移，并未真正解决问题。csrc/rocm/attention.cu 中的 CALL_CUSTOM_LAUNCHER_BLK_HEAD 仅分发 case 64 与 case 128，遇到其他取值均直接触发 TORCH_CHECK。这里的限制来自当前内核实现支持的形状，而不只是选择器的保守条件。

性能下滑中的一部分源于内核，而非架构。后继 checkpoint Qwen3.8-27B 在 vLLM 0.27 上于 2026-08-29 针对引擎可用于服务那 16 层的两个内核分别完成了测试。测试中的两组配置均未启用投机解码，运行于相同的 checkpoint 和会话，复现误差均优于 0.12 %。在默认配置下，ROCm 选择器会采用 ROCM_ATTN，因为 TURBOQUANT 与解码器不兼容，前者是其首先选用的回退内核。若改为锁定使用 TRITON_ATTN（仅需设置一个参数，无需任何补丁），相同的阶梯在 32 K 处提速 15.0 %，全区间的保留率也从 73.4 % 提升至 84.3 %。本文所讨论的性能下滑中，有十一个百分点取决于由哪个内核来服务那 16 层全注意力。其余的性能损失则与此无关：即使锁定了内核，该模型到 32 K 处仍损失了 15.7 % 的短上下文速率，这正是下一节探讨的主题。

5为什么回退路径在这个模型上特别慢

同一台机器上的稠密模型同样走这条 Triton 路径，却并未发生类似的性能劣化。二者的根本区别在于：在 batch 为 1 的解码阶段，内核究竟具备多少可供调度的并行度。

4 个 KV head、batch 1 留给内核的并行任务较少，难以充分利用 84 个 CU。以下两项观察更支持占用率不足，而非计算量更大的解释：

功耗随上下文增长而下降

在 518 token 时，双卡总功耗为 265 W + 265 W；而到 24 K 时，功耗反而下降至 232 W + 227 W。在整场测试扫描中，没有任何其他模型会出现功耗随深度下降的反常现象。其余所有模型均逐步攀升至 265 W 并维持高位，唯独该模型在中后段出现回落。各模型的基准功耗水平虽有不同（在 518 token 时，8B 为 245 W，12B 为 206 W，26B MoE 为 193 W），但关键的对比在于变化方向，而非绝对功率数值。功耗下降与计算单元未充分利用的解释一致。

按 KV 流量归一化后差距更大

在全网 64 层中，仅有 16 层需要维护 KV cache，且其 GQA 压缩比较高。其结果是，该模型在三者中读取的 KV 数据量实际上是最少的：每 token 仅需读取 64 KiB，相比之下 Qwen3-8B 需要 144 KiB，gemma-4-31B 则为 160 KiB。若按每 KiB 读取数据折算耗时，它达到了 Qwen3-8B 的 92 倍以及 gemma-4-31B 的 36 倍。因此，读取更多 KV 数据不能解释这里更高的耗时。

6对照：同一个模型换一个引擎

对照测试使用同一台机器、同一天、同一 checkpoint 家族，但更换推理引擎。两个引擎的量化格式不同，详见图 3。若对照的斜率显著更低，就不支持所有实现都会受到同样硬件限制的解释。

llama.cpp 的 ROCm 斜率落在稠密模型的 vLLM 测量范围内，Vulkan 斜率则低于该范围。明显更陡的曲线出现在所测的 vLLM 混合模型配置中，但这组对照没有隔离两个引擎之间的所有差异。

一个受到扰动的数据点 ROCm 后端在 16 384 token 处测得的速率为 21.35 tok/s，其标准差达到 2.635，而其余所有测试点仅在 0.06–0.09 之间波动；并且更深处的 24 576 token 速率反而更快。该点波动较大，不宜单独用于定量推断；具体原因未在此确定。它保留在图表中。

与此同时，该配置下的预填充表现却走向了另一个极端：其吞吐量随上下文长度增加反而上升，从 500 到 32 K 录得 802 → 881 tok/s，增幅达 9.9 %；而同场测得的每一条稠密对照组在相同区间内都掉了 36–44 %。发生反转的仅仅是解码阶段。（2026-08-31 更正：此处此前误记为 8–44 %。其中 8 来自 8B 模型，该模型的 500 token 档位未达到图表级精度，其两轮测量误差达 22 %，且原先引用了两者中偏高的一轮，从而掩盖了实际跌幅。在符合验收门槛的档位上，它从 1 K 起的跌幅达到 37 %，此处实测的任何稠密对照组跌幅均不少于 36 %。）

预填充吞吐量的上升属于当前硬件配置，而非该架构的固有属性。在 2026-08-31 之前，本文曾基于单一机器上单一模型手工记录的两个数据点，误将其归因为架构特征。Qwen3.8-27B 采用完全相同的 hybrid-SSM 设计，但在本测试机上其预填充速率并未上升：在 vLLM 0.23 下它下跌了 11.8 %，锁定在 Triton 时下跌 32.6 %；而在全宽链路上重新测试的对照组中，其表现为完全持平的 +0.3 %；在 A100 上它则下跌 8.1 %。（在 2026-09-02 之前，本句曾为该测试配置引用了 7.5 % 的跌幅数据。那次运行中有一张显卡协商至 PCIe 3.0 x8 速率；随后的 campaign-2026-09-02c 重新进行了测量，将该配置的走势由「下跌」修正为「持平」，但仍非「上升」。）（2026-09-03 更正：这句话原来写的是这个 checkpoint 的预填充「从来没有上升过」。然而在 H100 上，同一模型在相同的测试档位下上升了 19.4 %，增幅甚至超过了本节讨论的 Qwen3.6 测试配置。原先的论断将特定机器上的实测结果误推演为模型架构的一般结论。）与此同时，完全不含任何线性注意力层的 MoE 模型 gemma-4-26B-A4B，其预填充吞吐上升幅度同样超过了 Qwen3.6，在 7 月为 23.8 %，8 月为 21.9 %。目前收录于 benchmarks/prefill.jsonl 中的二十一条 stock hybrid-SSM 阶梯（涵盖同一 checkpoint 家族跨九种机器配置的测量）显示：七条阶梯上升超过 1 %，一条持平，十三条下降。相同的 Qwen3.8-27B checkpoint，其预填充变化幅度从双卡 Radeon 上 2026-09-07 那条到 128 000、锁定 TRITON_ATTN 的阶梯的 −68.3 %，一直延伸到双卡 H100 上的 +103.0 %。同一种架构和同一个 checkpoint，产生了横跨 171 个百分点且正负符号截然相反的测试结果。这就是核心发现：预填充吞吐曲线的上升，仅仅说明在该测试配置上短 prompt 的固定开销压过了计算复杂度的二次增长项，并不意味着模型内部维持着某种循环状态。无论预填充走势如何，本文所记录的解码阶段性能崩溃均不受影响：那是直接实测得出的客观事实，并非依赖此类推论得出。

7修复，测了两次

上游给出的修复补丁是 vllm#45916。该 PR 为 Triton 回退实现引入了一个 split-KV 解码内核：执行方式不再局限于每个（序列，KV head）由单个 workgroup 遍历全部上下文，而是将整个 KV 缓存区间切分给多个 workgroup 并行处理，最后再执行规约操作。这恰好补齐了该模型所匮乏的并行度。

我们最初于 7 月在 vLLM 0.23.1 上对此进行了初步验证。当时在轻微不同的上下文深度下进行单次差分测试，在 32 K 处录得了 2.52 倍的提速。随后，我们在 0.27 镜像上做了一次受控 A/B 测试：测试的两组配置运行于完全相同的软件栈与测试 harness 下，每个测试格均启动全新容器，并且仅替换对应的内核文件；整套测试重复运行两轮，并在第二轮中颠倒两组配置的执行顺序。

两轮测试数据汇总后显示：1 K 处提速 1.38 倍，8 K 处为 3.52 倍，32 K 处达到 9.46 倍。在 32 K 上下文下，单 token 解码耗时从 261.9 ms 大幅缩减至 27.7 ms，衰减斜率从 7.408 锐降至每 1 000 token 上下文 0.262 ms，而 1 K 到 32 K 的性能保留率也从 10.2 % 跃升至 70.0 %。性能崩溃的现象彻底消失了。

8没有被确立的部分

列举四项局限。

A/B 有一格是双峰的

在 8 192 token 处，打补丁的配置在四轮测试中分别跑出 47.02、40.14、47.58 与 42.41 tok/s。经排序后，中间数值的落差占据了总极差的一半以上：这代表相距约 15 % 的两个独立模态，而非随机噪声。加跑第三、四轮后极差从 15.8 % 扩大到 16.8 %。确定性的切分启发式算法不可能导致这种现象，其底层机理尚未确立。正文引用的 3.52 倍均值对任一聚类均无法准确描述。

图 4 是另一个模型、另一套栈

图 1 测试的是 0.23.1 上的 Qwen3.6-27B；图 4 则是 0.27 上的 Qwen3.8-27B。更新的软件栈启用了不同的 W4A16 线性内核，在不计入注意力机制的情况下便能单独带来约 3 倍提速。两张图中的绝对性能数值不具可比性，但比值关系与曲线形态依然成立。

因果 A/B 只有一台机器

因果 A/B 测试全程在单一机型、单一芯片厂商且 batch 为 1 的受控条件下完成。在四张租用的 NVIDIA 显卡上延伸至 128 000 token 的解码阶梯显示，Qwen3.8-27B 在 H100 上降幅为 21.8 %（与稠密 31B 模型相当）。尽管各厂商硬件均由注意力机制决定上下文深度开销，但由于各卡选用的后端各异，无法构成纯粹的同内核对照。占用率假说预测增大 batch size 能缓解性能崩溃，但本文对此未做实测。

这个修复没修掉的东西

Paged attention 占整个解码步耗时的比例由约 68 % 降至 11 %。其余耗时主要被量化 GEMM 占据，其在短上下文时约占总时间的 77 %。本文所修复的是斜率问题；而基准吞吐量的优化则属于另一个独立范畴。

9此后发生的变化

本文是一份带日期的记录，而非长期适用的既成结论。在上述测量完成之后，已有三项事实发生了变动。

2026-08-10 · gate 不再需要谁去放宽 7 月的验证在本地将 on_gfx12x() 放宽为 on_gfx1x()，以便 gfx11 能调用新内核。该修改已于 2026-08-10 合并至 vllm#45916 自身的分支，因此该 PR 目前已原生支持 RDNA3，不再需要任何本地修改。
2026-08-28 · 基线那个问题有答案了 7 月的文稿最终停留在「斜率问题已解决，基线表现则是另一个问题」。图 4 中的 0.27 A/B 测试给出了确切答案：在 32 K 深度下，该模型的解码速率现已提升至 36.1 tok/s（最初 campaign 测得的数据为 4.2）；且其残余斜率完全落入了本机稠密模型产生的基准区间内，不再高出 27 %。
2026-08-29 · 本文有两个数字和它自己的图对不上 摘要初稿曾称混合模型的衰减曲线比稠密模型「陡四到四十倍」。对照图 3 所绘制的基线区间（每 token 0.118 到 0.339 µs），混合模型的 4.84 对应的是 14.3× 至 41.0× 的陡度，其下界应为十四而非四。此外，「llama.cpp 的斜率落在区间之内」的论断仅对 ROCm 后端成立，Vulkan 后端实测为 0.107，完全低于该区间。以上两处均已完成就地更正，verify_doc_figures.py 现已对这一比值及两个后端相对基准区间的位置进行了刚性校验。
