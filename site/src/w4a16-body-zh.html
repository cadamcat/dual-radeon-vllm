12 tok/s 是两个问题

一个 27B 模型在这台机器上解码只有 12 tok/s，而本仓库此前所有文档都把它当成一个故障、 一个原因。它其实是两笔叠在一起的开销：一笔与上下文无关，一笔随上下文增长。分开它们只需要一次 A/B； 分开之后会发现，两笔各自都已经有了上游修复，而且都不是我们做的。

__CHIPS__

摘要

同一个模型家族，非对称打包与对称打包相差 1K 上下文 3.241×、8K 1.786×、32K 1.266×。按比值读，像是一个正在消退的效应。按每步解码耗时读，结论恰好相反：两臂之差始终落在 58.03 到 62.79 ms 之间，散布 8.2 %，而比值下降了 60.9 %。 一笔固定开销压在一笔增长开销下面。

固定的那笔是 W4A16 线性 kernel。非对称 checkpoint 以 uint4 抵达， 而 SUPPORTED_QUANT_TYPES 只收 uint4b8，这一层就静默地退回 Triton。 没有任何警告，模型名字也不告诉你手上是哪一种。

增长的那笔是 paged attention，它有自己的一篇。 两半如今都已在上游修好，而且两个修复都不是我们做的： vllm#40977 加了第二个确实接受 uint4 的原生 kernel， vllm#45916 放宽了 split-KV 的注意力门槛。

这篇文章贡献的是"把两者分开"，以及分开途中发现的一件事：在 gfx1100 上扫过非对称配置空间， 十二个配置里有三个被两个 kernel 同时接受、一个只剩 Triton， 另外八个根本没有任何 kernel 能服务。所有带 act-order 的非对称 checkpoint 都落在最后这一档。

1测的是什么

这里的解码速率是差分测量，不是服务端自报的数字：生成 8 个 token，再生成 64 个， 用多出来的 56 个除以多出来的时间。这样可以把 prefill 和首 token 的开销从一个本该描述稳态解码的数字里剔掉。 每个格子都在原版镜像上起一个全新容器，先跑一次预热生成并丢弃。

预热不是走过场，它有它的理由。每个格子恰好 JIT 编译四个 Triton kernel，两臂上这四个都落在预热里， 所以两次计时调用都不带编译。这一点是从容器日志里核过的，不是假定的；而且两臂都核过， 免得某一侧被编译时间抬高。

这些层究竟走的是哪个 kernel，是从 worker 内部记下来的。在 --tensor-parallel-size 2 下线性层是在 spawn 出来的进程里构造的， 在父进程里打的 monkeypatch 在那边什么也看不到。所以 choose_mp_linear_kernel 是在引擎启动前直接改在磁盘上的，每个 rank 各写各的判定。本文每个格子都带两个不同的 pid； 若某次插桩根本没到 worker，它会写下一条空记录然后以 0 退出。

这些绝对值值多少 这是一台 VFIO 直通的虚拟机，两卡之间没有 P2P，走的是跨 die 的 PCIe 3.0， 这是刻意挑的最不利拓扑而非展示配置。这里的形状可以外推，绝对水平是下界。 不同容器镜像上测的格子彼此之间不可作绝对比较，图 3 标出了适用范围。

2被它替换掉的那个结论

2026-08-24 这台机器同一天测了两个 27B 模型：一个稠密模型 44.8 tok/s， 这个混合 SSM 模型 12.3，在参数量固定的前提下相差 3.64×。 当时把它读成了架构结论，仓库自己的文档也是这么写的。

这个读法有混杂。那次 campaign 里除了两个 Qwen3.x AWQ checkpoint，其余全是对称的， 而那两个恰好就是文档里点名"慢"的那两个。架构对比和打包差异，正好在得出结论的那一点上重合。 下面这次 A/B 就是用来把它们分开的，而打包本身值到 3.24×。

3一个家族，两种打包

同一个模型的两个 checkpoint —— Qwen3_5ForConditionalGeneration， 两边都是 compressed-tensors pack-quantized，同两张卡、同一镜像、每格一个全新容器。 一个是 symmetric: false，另一个 symmetric: true。

每 token 的解码时间是可加的。如果原因是每步一次 GEMM，那它必须表现为 一个与上下文无关的毫秒数，比值下降只是因为两臂下面的注意力项在长大。 这是比值本身给不出的预测，也是这张图默认显示毫秒而不是那个看起来更大的倍数的理由。

4为什么其中一个拿得到原生 kernel

自 vllm#41394 起， vLLM 就有了 gfx1100 上的原生 W4A16 kernel，注册在 compressed-tensors 用的同一条混合精度路径上， 它自己的 docstring 写着"在 ROCm-RDNA3 路径上注册在 Triton kernel 之前"。能不能走到它，由一行代码决定：

vllm/model_executor/kernels/linear/mixed_precision/rdna3_w4a16.py
SUPPORTED_QUANT_TYPES = [scalar_types.uint4b8]

uint4b8 是对称 int4。compressed_tensors_wNa16.py 按 checkpoint 自己的 symmetric 标志挑权重类型，并设 zero_points = not symmetric， 于是非对称 checkpoint 以 uint4 抵达并卡在类型检查上。直接问注册表，它就是这么说的：

choose_mp_linear_kernel，从 TP worker 内部记录
no        RDNA3W4A16LinearKernel   Quant type (uint4) not supported by
                                   RDNA3 W4A16 kernel; supported: [uint4b8]
SELECTED  TritonW4A16LinearKernel

没有任何警告。模型照常加载、照常运行、答案也对，就是慢。

两臂之间另外两处差异必须实测排掉，不能靠讲道理排掉。group size，32 对 128： 没有任何 checkpoint 能把它与对称性分开，所以这次 A/B 分不开；但 can_implement 的源码里根本没有 group-size-128 这个条件，上面四个角也忽略它，而这台机器上最快的模型就是 group 32。 哪些层被量化：两边的 ignore 列表不同，所以量化线性层是从各自的 model.safetensors.index.json 里数出来的，不是假定的。399 对 400， 差的正是一个只有对称 checkpoint 才量化的层 —— 那反而给对称臂多了一次 W4A16 GEMM， 所以它不可能是对称臂更快的原因。

5另一项

那个固定块是两臂之差的全部，却远不是解码步骤的全部。在 32K 上两臂的绝大部分时间都花在 kernel_paged_attention_2d 里，它的单次调用耗时在 1K 到 32K 之间涨了 28 倍， 而 profile 里其他每一个 kernel 都是平的。这就是第二个问题，它和量化毫无关系， 有自己的一篇文章和自己的修复。

有这两项，就能解释为什么任何一个标题数字都不是好总结。1K 上打包罚金几乎就是全部差距； 32K 上它在注意力面前只是舍入误差。一个不带上下文长度的比值， 掩盖的正是"它主要在测哪一个"。

6两个修复，都不是我们做的

vllm#40977 在 2026-07-14 合入， 加入了 RDNAHybridW4A16LinearKernel，它接受 uint4、group size 32 以及整个 gfx11。所以在当前 main 上，非对称 checkpoint 确实拿得到原生 kernel —— 只不过是另一个 kernel，走的是放宽注册表而不是放宽类型门。同一个在 Triton 上跑出 11.41 tok/s 的 checkpoint，在那边是 37.32。

vllm#45916 是注意力那一半， 本仓库对它的贡献是 gfx1100 上的端到端验证，不是代码。

一个跨 campaign 的对照让 0.27 这一臂本身也站得住。1K 的 stock 格子被 split-KV 那次 campaign 测了两遍，另外还有一次是几周之后、由另一个脚本作为本目录里 kernel 对比的 hybrid 臂测的。两次 campaign 相差 0.21 %，并且谁也没有向谁靠拢过。

7剩下的那部分，以及它为什么还不是一个 PR

类型门是可以打开的。打开之后会暴露出藏在它后面的第二个问题，而这才是值得报告的部分： checkpoint 交付的零点布局是 (N/8, groups)，kernel 要的是 (groups, N/8)， 于是这一层选中了、加载了，然后在 kernel 入口以 b_scales must have same group count as qzeros 拒绝。 HIP kernel 从来没有拿着错的数据跑过，它在门口就把形状挡回去了。

三行 Python 同时修好两半：放行 uint4；跑一次 process_weights_after_loading 已经在对另外两个张量做的转置； 以及把 kernel 一直支持的那个零点约定传进去，而不是写死 GPTQv1 的那个。 在 0.23.1 上是 3.11×，输出与 Triton 对照逐 token 一致。

让人相信第三行的是那条对照臂 只做前两处改动的那一臂跑出 35.45 tok/s，对 35.50， 所以它确实在执行原生 kernel。它的平均 logprob 差 24 倍，输出是 terasterasterasteras…。一个止步于布局修复的 patch， 在除正确性之外的每一个维度上都会看起来像成功。

但在 main 上它仍然是错的 patch。在 Hybrid 也能接的配置上 Hybrid 快 5.9 % （37.32 对 35.22），而 RDNA3W4A16LinearKernel 在 ROCm 优先级表里排在 Hybrid 前面，所以在那里放行 uint4 等于把这一层交给两个能用的 kernel 中较慢的那个。 而这个 patch 没有办法把这种情况和"它是唯一选择"的情况区分开。

这八个是用数值核过的，没有停在注册表的说法上：真实的 desc_act 置换， 对照一个通过 g_idx 索引 scale 和零点的 fp32 参考实现，fp16 与 bf16、decode 与 prefill 形状都跑。patch 前四例失败，patch 后四例通过，整个测试套件到 54 通过且无回归。

事情就停在这里。不是 PR，因为"只要那九个、不要那三个"需要一个属于优先级表主人的决定； 而同样的论点已经有人从 gfx1151 那一侧在 vllm#46186 上讲过了。 更可能是上游想要的做法是去放宽 Hybrid，而那不是我们该改的代码。

8没有被确立的部分

那笔固定开销是否只有 GEMM

可加分解与"一笔不随上下文变化的每步开销"一致，kernel 记录也说明了跑的是哪个 GEMM。 但这本身并不能排除另有一项固定开销搭在里面。被测到的是：两臂之差在 32 倍上下文变化里平到 8.2 %， 以及两臂由不同的线性 kernel 服务。

精度

这是两个发布方在不同 group size 下各自独立量化的结果，这里只测速度。 "在 RDNA3 上优先选对称 checkpoint"是一句吞吐结论。这两个模型是否一样好，这里什么也没回答。

结论能走多远

一台机器、一个模型家族、只有 gfx1100、只有 TP=2、只有 bf16 激活。 partition_scales 与逐通道参数路径完全没有触及，permute 假定的是分组量化的布局。 覆盖扫描是注册表对合成参数的判定；那九个配置里究竟有多少真的有人在用，没有测。

A/B 每格只有一次 run

六个格子，各起一次容器。已有的重复只覆盖对称臂，把它移动了至多 1.31 %。 图 3 里 0.27 的两臂每格两次 run，并带各自的区间。

9此后发生的变化

2026-07-14 · 兜底不再是 Triton vllm#40977 合入， 加入 RDNAHybridW4A16LinearKernel。在 main 上非对称 checkpoint 能拿到原生 kernel，"退回 Triton"这个说法只适用于 0.23.x 以及没有这个 PR 的构建。 关于 RDNA3W4A16LinearKernel 自身的一切 —— 类型门、转置的零点布局、 use_v2_format —— 在 main 上都没有变。
2026-08-27 · 在 0.27 上实测，而第一次读法太宽 在 0.27.1.dev5 镜像上的这一对让 Hybrid 领先 5.9 %，当时写下的是"这个 patch 是净亏"。 它是在那个配置上净亏。第二天的扫描找到三个它会挤掉更快 kernel 的配置， 以及九个它是唯一选择的配置，结论随之收窄。
2026-08-28 · campaign 里的架构结论已就地更正 两个 27B 模型之间的 3.64× 曾被归因于架构，而它与打包混杂。 README.md、docs/benchmarks.md 与 docs/architecture-notes.md 里受影响的陈述已更正并标注日期，docs/open-questions.md §9 标记为已回答。 没有受影响的是：每一条斜率结论，以及那四个都在各自最佳 kernel 路径上的模型之间的排序。
写测试改变了这个 patch 第一版把零点约定挂在 c.zero_points 上。它通过了端到端运行，却弄坏了十个已有用例， 因为 GPTQ checkpoint 会显式存零点、同时仍然使用 v1 的 "+1" 偏移。正确的键是 not c.weight_type.has_bias()。挂在 zero_points 上会让 RDNA3 上每一个非对称 GPTQ checkpoint 被静默反量化错，而那次本该验证它的运行还是会通过。

每张图背后的数据。A/B、强制换 kernel 的那次运行、三行修复及其对照臂、 覆盖扫描以及提给上游的测试用例都在 benchmarks/w4a16-symmetry/， 连同每个格子在 worker 内部记录的 kernel 判定。本页每一张图都由 verify_doc_figures.py 从这些文件重算，任何一处对不上就非零退出。
