The RCCL crash was never about RCCL

Two Radeons, --tensor-parallel-size 2, and a message that sends everyone to the wrong layer: the operation cannot be performed in the present state. Thirteen hypotheses, twelve of them wrong, and a fix that for virtual machines turns out to be one line of configuration rather than a rebuilt library.

__CHIPS__

Abstract

On a machine without PCIe AtomicOps, every RCCL collective fails at dispatch with hipErrorIllegalState. The cause is four layers below RCCL: since ROCm 7.2 the shipped device kernels declare a hostcall buffer, ROCr can only build one when the PCIe path provides AtomicOps, and without it the dispatch is refused before any collective runs.

The chain reduces to thirty lines of HIP that use neither RCCL, PyTorch nor vLLM: two kernels with an identical launch path, one of which calls device printf. The plain one passes; the one needing hostcall fails with the production error.

Twelve competing explanations were tested and eliminated, including two this project believed and published before disproving them: that it was an RCCL version regression, and that the ROCm runtime was gating kernel submission in guests.

The remedy this repository first verified is a rebuild of RCCL with NDEBUG reaching the device compile. The fix that matters more was found later: on a passthrough guest the missing capability is usually self-inflicted by one line of VM configuration. QEMU advertises AtomicOp completer support automatically, and declines only when the card is handed over as a multifunction device — which is the Proxmox default.

1The failure, and where it sends you

Two GPUs, tensor parallelism, and this at engine start:

The error surfaces inside RCCL's enqueue.cc, so people debug RCCL. Then ROCm. Then the kernel. The message that names the actual cause is one line above the failure and mentions neither the library nor the collective, and it only appears at log level 4.

2The causal chain

Five links. Each was established by evidence that does not depend on the link below it.

3Thirty lines that take RCCL out of the picture

Link 4 is the one that carries the argument, because it can be tested without any of the software the failure appears to be about. Two kernels, identical launch shape; the only difference is that the second calls device printf, which requires a hostcall buffer.

diagnose/hipgate3.cpp · no RCCL, no PyTorch, no vLLM
--- dev0 ---
[plain    ] launch:no error   sync:no error
[hostcall ] launch:no error   sync:the operation cannot be performed in the present state

The same string, from thirty lines of HIP, on one GPU, in half a second. That is what turns a library-version story into a platform-capability story: the failure has nothing to do with collectives. It reproduces for any kernel that needs a hostcall, and RCCL's kernels need one because they carry device-side assert().

4Why "downgrade the library" works, and what it actually shows

The community answer is to install the ROCm 7.1.1 build of librccl. That works, and it is evidence for this root cause rather than against it. Counting hostcall declarations in the shipped device images:

So the newer RCCL is not broken in general. It requires a platform capability that these machines never had. The same reading unifies the virtualised reports with the bare-metal ones: if those bare-metal platforms did route AtomicOps, the hostcall requirement would be satisfiable and downgrading would not help. That downgrading helps is itself evidence that they lack atomics too.

The version correlation is real and the causation is not Building 2.27.7-b38 from source on the current toolchain fails identically, because that build does not get NDEBUG to the device pass either. The variable is hostcall, not the version number. This is the first of the two conclusions this project got wrong and published before disproving.

5What was ruled out

Thirteen hypotheses were live at some point. Twelve are wrong. They are listed because the next person should not have to re-run them, and because two of them were ours.

The second thing we got wrong "ROCm ≥ 7.13's HIP runtime gates kernel submission in VFIO guests" was published here and is false. diagnose/hipgate.cpp issues the exact hipExtLaunchKernel form with a completion event, 4 KB kernargs, cross-stream waits and fine-grained host memory, and all of it passes on 7.14. Submission is fine. Only hostcall-carrying kernels are refused.

6The fix that mattered was one line of VM configuration

The remedy verified first was a rebuild: compile RCCL with NDEBUG reaching the device pass, which removes the assert() that pulls hostcall in. That works on RCCL 2.27.7, which is where it was verified end to end, and for a while it was the whole answer. It is not sufficient on 2.30.4, where the declaration survives a build with no hostcall-calling instructions left in it — §8.

A rebuild is the wrong first move for a virtual machine. QEMU already knows how to advertise AtomicOp completer support on an emulated root port — vfio_pci_enable_rp_atomics() has done it automatically since v8.1.0 — and it gives up under a short list of conditions, one of which is that the device is passed as multifunction. Proxmox's default hostpciX form hands the GPU over together with its audio function, which takes exactly that branch.

7Then who is the rebuild for

Everyone whose hardware genuinely cannot deliver AtomicOps, which is not a small group:

  • cards behind a consumer chipset switch, on bare metal — this is the case ROCm#6520's independent bare-metal reproduction hit, and no amount of VM configuration helps it
  • hosts whose root ports do not advertise completer support at all
  • QEMU older than 8.1.0
  • any case where the card must keep its audio function inside the guest

The mechanism is unchanged for them, and the NDEBUG rebuild is what this repository verified. What changed is the ordering: in a VM, check the configuration before rebuilding anything.

One command decides which case you are in dmesg | grep "PCIE atomic" — output means affected; silence is not the other way round, only inconclusive, so follow it with the lspci check below. Grep that exact phrase; a bare grep -i atomic also matches unrelated DMA: preallocated ... pool for atomic allocations lines from early boot. If you are affected and in a guest, look at lspci -vv on the root port above the card before you build anything.

8What is not established

Whether the audio function can be kept another way

Passing the GPU as a single function leaves its audio function behind. Whether the two can be split across separate emulated root ports so that the guest keeps both the audio device and atomics was never tested here.

What AMD intends

Whether the hostcall dependency is kept or removed is an upstream decision, and ROCm#6520 is open. On RCCL 2.30.4 the declaration survives a build with zero hostcall-calling instructions — NDEBUG removes every __ockl_* symbol and the metadata entry is still emitted during the device link — so removing the device-side assert() would no longer be sufficient on current RCCL.

One machine for the VM half

The configuration A/B is one host, one QEMU version, one board. The QEMU condition is source, not inference, but its consequences on other boards are not measured here.

9What has changed since

2026-08-23 · this machine now has atomics The guest was reconfigured to single-function passthrough and has advertised completer support since. Stock unpatched RCCL 2.30.4 now runs 135 of 135 cold communicator initialisations correctly here, so the box that was this repository's counterexample on the atomics axis no longer is one.
2026-08-28 · the severity claim was narrowed This report originally said every QEMU root port declines completer support regardless of what sits behind it, and concluded that any VFIO passthrough guest is affected, virtualised Instinct included. That is wrong for a single-function passthrough. The upstream issue body and the comment it cites were both corrected; the claim now reads that a passthrough Instinct is affected when passed as multifunction and not when passed as a single function.

Reproduce it yourself. The thirty-line gate is diagnose/hipgate3.cpp and needs neither RCCL nor PyTorch. The platform check is diagnose/check-platform.sh. The full evidence chain and the elimination matrix are docs/root-cause.md; the VM half is docs/vfio-atomics.md.

Reported upstream as ROCm#6520, where @adderek independently reproduced it on bare metal with IOMMU disabled, and @bkvargyas contributed the switch-versus-atomics trade-off from the other side of it. Related: ROCm#6074, vllm#38587.
