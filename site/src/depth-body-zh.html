摘要

长上下文基准通常报告的是保留率：模型在深处还剩下短 prompt 速率的百分之几。在 campaign-2026-09-03 的六条臂上，这个数给出的排序几乎是它们实际付出的成本排序的反面。原因是算术而非玄机：保留率是把深度成本除以基线，而这六条臂的基线跨 8.4×。集合里最慢的那个模型，看起来最抗深度。

替代方案也并不安全。把每 token 毫秒数对上下文做拟合，得到的斜率单位是「每上下文 token 微秒」，它是成本而不是比值，不携带基线。在这一对卡上，这个斜率是更好的描述——但它同样不是模型的性质。同一个 Qwen3.8-27B checkpoint，同样的两张卡、同样的权重、同样的上游补丁，在三套只差一个 vLLM 版本和一个 serve 参数的软件栈上，分别测得 0.350、0.233 和 0.117 µs/上下文 token。这是 3.00×，足以把它从这个集合的最后一名挪到第三名。

其中后端那一段是归因，不是并列比较。两种注意力后端是在同一次运行的两个会话里测的，而第三个会话重复了第一条臂，用来给会话边界定价：最多 0.50 %，而两臂之间的差距达到 48 %。两者的截距吻合到 1.5 %，斜率却差 2.11×——也就是说这个参数动的是深度项，基线原封不动。它的代价在预填充：到 128 000 token 时解码优势张开到 1.48×，而预填充掉到 0.44×，并且在这台机器能撑住的最深一档上，两者都还没有掉头。

1两个数，而它们不一致

下面每条臂都是同样两张卡上的同一条阶梯，TP=2，batch 1，来自 campaign-2026-09-03。 它们的最深档并不相同——8B 停在 32 000，另有三条到 128 000——所以两列都在每条臂都有的跨度上计算，即 500 到 32 000。在更长跨度上取的斜率是另一个数，拿它和这个比，比的是曲率。

2百分比究竟在除以什么

这个反转既不是悖论也不是测量错误。保留率就是 1 − 成本 × 深度 / 基线，所以基线大的臂会把大的成本藏起来。这六条拟合的截距——也就是在读到任何上下文之前，一步解码本身要花多少——跨 ，从 MoE 最快的一步到 hybrid SSM 最慢的一步。在 32 000 个 token 上，这个 hybrid 每 token 付出的成本是这里最高的，而它仍然只相当于它原本就在花的那一步的八分之一。它看起来抗深度，是因为它慢。

它诱导出的读法恰恰相反：保留率百分比奖励慢的基线。两个深度行为完全相同的模型可以有不同的保留率；而两个保留率相同的模型，深度实际花掉它们的代价可以差好几倍。

3同一份权重，三套栈

如果斜率是更好的那个数，下一个问题就是它究竟属于谁。这个 checkpoint 现在已经在三套软件栈上测过，权重、卡、并行度、阶梯以及 vllm#45916 的 split-KV 补丁全部保持不变：ROCm 7.14 上的 vLLM 0.23.1，也就是那个 campaign 发布的臂；ROCm 10.0 上的 vLLM 0.27.1，即 campaign-2026-09-06；以及同样的 0.27.1 再加 --attention-backend TRITON_ATTN，即 campaign-2026-09-07。

这三条线之间，模型本身没有任何变化。跨度是 ，而它足以把这个 checkpoint 从图 1 成本排序的最后一名挪到第三名——越过那个 MoE，并且和只有它四分之一大的 Qwen3-8B 只差一线。

4为什么最后那一步是后端而不是会话

后端在服务启动时就定了，所以两条 0.27 的臂不可能共处一个会话；那么 A 与 B 的差异只有在会话边界的代价小于它时，才是后端的差异。这个仓库正是在这件事上栽过： rccl-ndebug-ab-2026-09-04 曾发布过一个 3.6 % 的「臂效应」，后来查明是会话顺序。所以这次运行有第三个会话：在第二条臂结束之后，用三个档位重复第一条臂。

还有两件事让这一对成为归因而不是赛跑。两条拟合的截距吻合到 1.5 %，斜率却差 2.11×：这个参数动的是「一个上下文 token 值多少」，而「一步值多少」原封不动。 以及方向在预填充上反了过来——那是权衡的形状，而不是某一条臂单纯更好。

5这个权衡还没有掉头

campaign-2026-09-02c 把这两个后端测到 32 000 token，发现它们在互相交换，而且在它停下的地方两个差距都还在张开。到四倍深度上，它们仍在张开：128 000 处解码到达 ，预填充到达 。没有哪个后端是更好的那个。它们把同一份成本在预填充和解码之间做了不同的划分，而哪种划分更合适，是关于流量的问题。

6那条曲线不是直线的臂

图 1 里有一行携带的是警告而不是测量。Muse-Glimmer-30B 的线性拟合只有 ，而其余每条臂都在 以上。它的 attention 走 2 048 token 的窗口，所以它每 token 的成本是停止增长而不是增长得更慢，而一条直线说不出这件事。 它的斜率之所以列出来，是因为删掉比带着限定印出来更糟，但它和其余那些不是同一类数字，不应该和它们一起排序。

这也是为什么这一类斜率旁边要报 r²：它告诉读者，眼前这个单一数字究竟描述了它所拟合的那条曲线，还是只是概括了它。

7该报什么

报两个数而不是一个，再加第三个用来说明前两个是否有意义：截距，即在有上下文之前一步解码的成本；斜率，即每个上下文 token 追加多少；以及 r²，说明这个拟合是描述还是概括。保留率百分比可以从前两个在任意深度上推出来，而它们都无法从保留率推回去。

这一切都没有把斜率变成模型的性质。在这台机器上，它是模型和为它服务的那个内核共同的性质，而且后一项更大：软件带来 ，而图 1 成本那列里六个不同 checkpoint 之间只差 2.7×。

8哪些没有被确立

  • 只有一个 checkpoint 在两种后端上都测过。其余五个会不会同样移动并不知道，而且它们无论如何也不能在 0.27 上一起重跑：gemma-4 的 Quark 插件读到异构的 head_dim 就会在加载前死掉。
  • 这里没有打开任何一个内核。预填充朝反方向走，是权衡的形状，不是对权衡的解释。
  • 每一格都是 batch 1。max-num-seqs 设为 16 是为了容量，不是为了负载。两个后端在深度上的并发表现是另一次测量。
  • 图 1 的六条臂来自一台机器。「百分比在除以什么」这个论断是算术，可以带走；而那个具体的排序属于这一对卡。
