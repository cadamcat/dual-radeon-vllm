保留率、解码成本与软件栈

摘要

长上下文测试常用保留率表示较长上下文的解码速率相当于短上下文速率的多少。在 campaign-2026-09-03 的六组配置中，按保留率排序，结果几乎与按每上下文 token 新增耗时排序相反。这六组配置的基线单步耗时相差 8.4×，因此相同的新增耗时可能对应很不一样的百分比变化。

斜率也受软件栈影响。将每个解码 token 的耗时与上下文长度做线性拟合，可以得到每增加一个上下文 token 所增加的耗时。在同样两张卡、同一份 Qwen3.8-27B 权重上，三组测试的斜率分别为 0.350、0.233 和 0.117 µs/上下文 token。跨版本测试改变了 vLLM、ROCm 和权重内核；vLLM 0.27 内部的对照只改注意力后端参数。整体相差 3.00×，使该模型在成本排序中从最后一名升到第三名。

后端 A/B 测试加入了重复基线，以检查会话间波动。两个会话分别测试两种后端，第三个会话重复第一组配置。重复测量之间最多相差 0.50 %，而后端之间的解码速率差距达到 48 %。两条拟合曲线的截距相差 1.5 %，斜率相差 2.11×，说明后端切换主要影响随上下文增长的开销。到 128 000 token 时，Triton 的解码速率是 ROCM_ATTN 的 1.48×，预填充速率则为 0.44×。

1保留率与成本给出不同排序

下面的配置均来自 campaign-2026-09-03，使用同样两张卡、TP=2、batch 1。各配置达到的最大上下文长度不同：8B 到 32 000，另有三组到 128 000。因此，两项指标都在共有的 500–32 000 token 范围内计算。曲线并非直线时，改变拟合范围也会改变斜率。

2百分比究竟在除以什么

排序变化来自基线与新增耗时的共同影响。1 − 成本 × 深度 / 基线 表示这种基线依赖关系。六条拟合曲线的截距，即外推到零上下文时的单步解码耗时，相差 ，最低的是 MoE，最高的是 hybrid SSM。在 32 000 token 范围内，hybrid SSM 的新增耗时最高，但仍只相当于其原有单步耗时的八分之一。它的高保留率主要反映了较长的基线单步耗时。

保留率不能单独衡量上下文带来的新增开销。两个模型每增加一个上下文 token 所增加的耗时相同，保留率仍可能不同；保留率相同的模型，新增耗时也可能相差数倍。

3同一份权重，三套栈

为检查软件栈对斜率的影响，同一个 checkpoint 在三套栈上进行了测试，权重、卡、并行度、阶梯以及 vllm#45916 的 split-KV 补丁全部保持不变：ROCm 7.14 上的 vLLM 0.23.1，即该批测试发布的配置；ROCm 10.0 上的 vLLM 0.27.1，即 campaign-2026-09-06；以及同样的 0.27.1 再加 --attention-backend TRITON_ATTN，即 campaign-2026-09-07。

三组测试使用相同的模型权重，斜率相差 。在图 1 中，这使该 checkpoint 从成本排序的最后一名升到第三名，超过 MoE，并接近参数量约为其四分之一的 Qwen3-8B。

4控制会话之间的波动

后端在服务启动时确定，因此两组 vLLM 0.27 配置需要分别启动会话。会话间波动可能影响比较。此前的 rccl-ndebug-ab-2026-09-04 测试曾把 3.6 % 的差距归因于配置，复测后发现来自会话顺序。因此，这次在第二组配置跑完后，增加了第三个会话，在三个上下文长度上重复第一组配置。

两条拟合曲线的截距相差 1.5 %，斜率相差 2.11×。这支持后端切换主要影响上下文相关开销，而非基线单步耗时的解释。预填充的变化方向相反，因此解码较快的后端并非在两项任务上都更快。

5更长上下文下的解码与预填充权衡

campaign-2026-09-02c 在 32 000 token 以内测得：Triton 解码更快、预填充更慢。延长到 128 000 token 后，差距仍在扩大，解码速率比达到 ，预填充速率比为 。选择哪个后端，取决于实际负载中提示处理与生成的比例。

6线性拟合不适用的情况

Muse-Glimmer-30B 的线性拟合较差，r² 只有 ，其余配置均高于 。该模型使用 2 048 token 的注意力窗口，限制了每 token 耗时的继续增长。这里保留斜率并标注局限，但不应将它与近似线性曲线的斜率直接排序。

报告斜率时应同时给出 r²，让读者判断直线对实际曲线的拟合程度。

7该报什么

建议报告三个量：截距，单位为每解码步骤毫秒数；斜率，单位为每上下文 token 微秒数；以及表示拟合程度的 r²。截距是模型外推到零上下文时的估计值，并非另做的一次零上下文测量。拟合结果可以用于计算指定上下文长度下的保留率，但仅凭保留率无法确定截距或斜率。

这些测量同时反映模型与实现的影响。在这台机器上，软件栈对照的斜率范围相差 ，超过图 1 中六个 checkpoint 之间的 2.7×。

8哪些没有被确立

  • 只有一个 checkpoint 在两种后端上都测过。其余五个会不会同样移动并不知道，而且它们无论如何也不能在 0.27 上一起重跑：gemma-4 在那个镜像上无法启动，因为 vLLM 0.27 的 Gemma4 converter 从按层存储的 transformers 配置里读取全局 head_dim，访问器在加载前就抛错（回溯；上游已在 vllm#49797 修正，0.27.1 不含）。
  • 这组对照没有采集内核级 profile。它测出了预填充与解码之间的权衡，但没有确定内核内部的原因。
  • 所有测试点均为 batch 1。max-num-seqs 设为 16 是为了容量，不是为了负载。两个后端在深度上的并发表现是另一次测量。
  • 图 1 的六组配置来自一台机器。保留率按定义依赖基线，但这里的具体排序只在这一对卡上测得。
