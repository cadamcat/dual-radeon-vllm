摘要

长上下文基准通常报告的是保留率：长上下文速率相当于短 prompt 速率的百分之几。在 campaign-2026-09-03 的六组配置上，这个指标给出的排序与额外解码耗时的排序几乎相反。原因在于指标的分母不同：保留率是把深度成本除以基线，而这六组配置的基线耗时相差 8.4×。基线最慢的模型，按保留率看受上下文增长的影响最小。

斜率也受软件栈影响。把每 token 毫秒数对上下文做拟合，得到的斜率单位是「微秒/上下文 token」，它描述耗时的增量，不以基线作分母。在这一对卡上，这个斜率是更好的描述——但它同样不是模型的性质。同一个 Qwen3.8-27B checkpoint，同样的两张卡、同样的权重、同样的上游补丁，在三套软件栈上（跨版本测试同时改变了 ROCm 和权重内核；vLLM 0.27 内的 A/B 仅改变注意力后端参数），分别测得 0.350、0.233 和 0.117 µs/上下文 token。这是 3.00×，足以把它从这个集合的最后一名挪到第三名。

后端 A/B 包含跨会话波动对照。两种注意力后端分别在两个会话中测试，第三个会话重复第一组配置，用来估计跨会话波动：最大为 0.50 %，远小于两组之间最高 48 % 的差距。两组拟合的截距相差不超过 1.5 %，斜率相差 2.11×，说明主要变化在随上下文增长的耗时，而非基线。Triton 的解码更快，但预填充更慢：到 128 000 token 时，相对 ROCM_ATTN 的速率分别为 1.48× 和 0.44×。在测到的最长上下文处，两项差距仍在扩大。

1两个指标给出不同排序

下面每组配置都是同样两张卡上的同一条阶梯，TP=2，batch 1，来自 campaign-2026-09-03。 它们的最深档并不相同——8B 停在 32 000，另有三条到 128 000——所以两列都在每组配置都有的跨度上计算，即 500 到 32 000。更长区间的拟合还会受到曲线弯曲程度的影响，因此不与这里的斜率直接比较。

2百分比究竟在除以什么

排序反转来自两个指标的定义不同。保留率就是 1 − 成本 × 深度 / 基线，所以较大的基线耗时会减小同一耗时增量对应的相对变化。这六条拟合的截距——也就是在读到任何上下文之前，一步解码本身要花多少——跨 ，从 MoE 最快的一步到 hybrid SSM 最慢的一步。在 32 000 个 token 上，这个 hybrid 每 token 付出的成本是这里最高的，而它仍然只相当于它原本就在花的那一步的八分之一。较高的基线耗时，使同样的额外耗时对应更小的相对速率下降。

较慢的基线可能对应较高的速率保留率。两个深度行为完全相同的模型可以有不同的保留率；而两个保留率相同的模型，上下文增加带来的额外耗时可以相差好几倍。

3同一份权重，三套软件栈

斜率衡量额外解码耗时，但它也会随软件栈变化。这个 checkpoint 现在已经在三套软件栈上测过，权重、卡、并行度、阶梯以及 vllm#45916 的 split-KV 补丁全部保持不变：ROCm 7.14 上的 vLLM 0.23.1，即该轮测试发布的配置；ROCm 10.0 上的 vLLM 0.27.1，即 campaign-2026-09-06；以及同样的 0.27.1 再加 --attention-backend TRITON_ATTN，即 campaign-2026-09-07。

这三条线之间，模型本身没有任何变化。跨度是 ，而它足以把这个 checkpoint 从图 1 额外耗时排序的最后一名挪到第三名——低于该 MoE，并接近参数量约为其四分之一的 Qwen3-8B 的结果。

4检查跨会话波动

注意力后端在服务启动时确定，所以两组 vLLM 0.27 测试必须使用不同会话。要判断后端的影响，需要先估计跨会话波动。此前，rccl-ndebug-ab-2026-09-04 曾将 3.6 % 的差异归因于测试配置，后续检查发现原因是会话顺序。因此，本次在第二组测试结束后增加了第三个会话，在三个上下文长度上重复第一组配置。

两组拟合的截距相差不超过 1.5 %，斜率却相差 2.11×。这一结果支持后端主要影响上下文相关耗时、而非基线耗时的解释。预填充的结果则相反，因此不能将解码加速概括为所有阶段都更快。

5最长上下文处的差距仍在扩大

campaign-2026-09-02c 在 32 000 token 内测得 Triton 解码更快、预填充更慢，两项差距都随上下文长度增加而扩大。扩展到 128 000 token 后，相对速率分别为 和 ，差距仍在扩大。后端选择需要结合请求的输入、输出长度和负载，而不能只看其中一个阶段。

7该报什么

建议同时报告截距、斜率和 r²。截距表示拟合得到的基线解码耗时，斜率表示每增加一个上下文 token 所增加的耗时，r² 用于说明拟合程度。可以用拟合结果计算指定上下文长度下的保留率，但单独一个保留率无法还原截距与斜率。

这一切都没有把斜率变成模型的性质。在这台机器上，它是模型和为它服务的那个内核共同的性质，而且后一项更大：软件带来 ，而图 1 成本那列里六个不同 checkpoint 之间只差 2.7×。

8测试范围与未验证事项

  • 只有一个 checkpoint 在两种后端上都测过。其余五个会不会同样移动并不知道，而且它们无论如何也不能在 0.27 上一起重跑：gemma-4 在那个镜像上无法启动，因为 vLLM 0.27 的 Gemma4 converter 从按层存储的 transformers 配置里读取全局 head_dim，访问器在加载前就抛错（回溯；上游已在 vllm#49797 修正，0.27.1 不含）。
  • 本次测试没有分析两个后端的内核实现。结果显示了解码与预填充之间的取舍，但没有解释其内核层面的原因。
  • 每组测试都是 batch 1。max-num-seqs 设为 16 是为了容量，不是为了负载。两个后端在深度上的并发表现是另一次测量。
  • 图 1 的六组配置来自一台机器。保留率受基线影响，但这里的具体排序仅代表这台机器上的测试结果。
