Long-context performance:
retention, decode cost and the software stack

The same Qwen3.8-27B weights differ by 3.00× in decode cost per context token across three software stacks

Six checkpoints were tested at the same sixteen context lengths on two RX 7900 XT cards. Qwen3.8-27B retains the largest fraction of its short-context decode rate, but adds the most time per context token. The two metrics measure different things. For this checkpoint, the latter also varies by 3.00× across software stacks.

Abstract

Long-context benchmarks often report retention: decode rate at a longer context as a fraction of the short-context rate. Across the six configurations in campaign-2026-09-03, this produces almost the reverse ranking of the added decode cost per context token. The baseline step times differ by 8.4×, so the same added time can represent very different percentage changes.

The slope also depends on the software stack. Fitting milliseconds per decoded token against context length gives the added cost in microseconds per context token. For the same Qwen3.8-27B weights on these cards, the slopes are 0.350, 0.233 and 0.117 µs per context token. The version comparison changes vLLM, ROCm and the weight kernel; the comparison within vLLM 0.27 changes only the attention backend flag. The overall 3.00× range moves this checkpoint from last to third in the cost ranking.

The backend A/B includes a repeated baseline to check for session-to-session variation. Two sessions measured the two backends; a third repeated the first configuration. The repeated measurements differ by at most 0.50 %, compared with a decode-rate gap reaching 48 %. The fitted intercepts differ by 1.5 %, while the slopes differ by 2.11×. The backend change mainly affects the context-dependent cost. At 128 000 tokens, Triton gives 1.48× the decode rate but 0.44× the prefill rate of ROCM_ATTN.

1Retention and cost give different rankings

The configurations below use the same two cards, TP=2 and batch 1, from campaign-2026-09-03. Their maximum context lengths differ: 32 000 for the 8B and 128 000 for three others. Both metrics are therefore calculated over the shared range of 500 to 32 000 tokens. Fitting over a different range can change the slope when the curve is not linear.

2What the percentage is dividing by

The ranking depends on the baseline as well as the added cost. The relation 1 − cost × depth / baseline illustrates this baseline dependence. The intercepts of these six fits — what a decode step costs before any context is read — span , from the MoE's fastest step to the hybrid SSM's slowest. Over 32 000 tokens the hybrid pays the most per token of anything here, and it is still only an eighth of a step it was already spending. Its high retention reflects its long baseline step time, not a low added cost.

Retention alone does not isolate the added cost of context. Two models can add the same time per context token but have different retention. Conversely, models with the same retention can differ substantially in added time.

3The same weights, three stacks

To check how the software stack affects the slope, this checkpoint was measured on three stacks with the weights, the cards, the parallelism, the ladder and the vllm#45916 split-KV patch all held: vLLM 0.23.1 on ROCm 7.14, which is the arm the campaign published; vLLM 0.27.1 on ROCm 10.0, which is campaign-2026-09-06; and the same 0.27.1 with --attention-backend TRITON_ATTN, which is campaign-2026-09-07.

The model weights are unchanged. The slopes span , moving this checkpoint from last to third in Figure 1, above the MoE and close to Qwen3-8B, which has a quarter as many parameters.

4Controlling for session-to-session variation

The backend is selected at server startup, so the two vLLM 0.27 configurations require separate sessions. That makes session-to-session variation a possible confounder. In an earlier rccl-ndebug-ab-2026-09-04 test, an apparent 3.6 % configuration effect was caused by session order. Here, a third session repeats the first configuration at three context lengths after the second has finished.

The fitted intercepts differ by 1.5 %, while the slopes differ by 2.11×. This supports a change mainly in the context-dependent cost, rather than in the baseline step time. Prefill changes in the opposite direction, so the faster decode backend is not faster for both tasks.

5The decode–prefill trade-off at longer contexts

campaign-2026-09-02c tested both backends up to 32 000 tokens and found faster decode but slower prefill with Triton. The differences continue to widen up to 128 000 tokens: the decode-rate ratio reaches and the prefill-rate ratio . The appropriate backend depends on the workload's balance of prompt processing and generation.

6When a linear fit is insufficient

Muse-Glimmer-30B has a poor linear fit, with r² of ; every other configuration exceeds . Its 2 048-token attention window limits further growth in per-token cost. The slope is listed with this caveat, but should not be ranked directly against the slopes of approximately linear curves.

Report r² alongside the slope so readers can judge how well the linear fit describes the measured curve.

7What to report instead

Report the fitted intercept in milliseconds per decode step, the slope in microseconds per context token, and r². The intercept is the fit's estimate at zero context, not a separate zero-context measurement. The fit can be used to calculate retention at a given context length, but a retention percentage alone does not determine either fit parameter.

8What is not established

  • Only one checkpoint was measured on both backends. Whether the other five would move the same way is not known, and they cannot be re-run together on 0.27 in any case: gemma-4 does not start on that image, because vLLM 0.27's Gemma4 converter reads a global head_dim off a per-layer transformers config and the accessor raises before loading (the traceback; fixed upstream in vllm#49797, which 0.27.1 lacks).
  • No kernel-level profile was collected for this comparison. The prefill–decode trade-off is measured, but its internal cause is not established here.
  • Every cell is batch 1. max-num-seqs is 16 for capacity, not for load. What either backend does under concurrency at depth is a different measurement.
  • The six arms of Figure 1 are one machine. Retention depends on the baseline by definition; the particular ranking was measured only on this pair.
