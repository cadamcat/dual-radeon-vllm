Eight ROCm kernel findings narrow to three on RDNA3,
and measuring another vendor removed two

Eight findings on RDNA3 classified across five hardware axes; checked against another vendor, kernel sources, and host topology

This repository's own summary describes RDNA3 as a second-class citizen in ROCm's kernel ecosystem, with eight write-ups grouped under that heading. Sorted by what the evidence actually supports, three of the eight are that. The rest are AMD-wide, vendor-neutral, or unrelated to the GPU — and separating them is the difference between a diagnosis and a grievance.

Abstract

The claim is real, but narrower than it appears. What survives as architecture-specific is a short list: a fast attention path this hardware falls off, a native quantised-linear kernel whose type gate excludes a common checkpoint class, and a performance heuristic written into one architecture's branch of a function while omitted from the other.

The purest instance is one line. use_rocm_custom_paged_attention requires gqa_ratio >= 3 on gfx11 and >= 1 on CDNA, for the same kernel. In the excluded range that kernel is 1.84× to 7.28× faster than the fallback it is passed over for, and the two bands overlap. The bound does not separate anything.

Four of the eight are not RDNA3 problems, and saying so is what the measurements were for. Two are vendor-neutral on distinct evidence. The same attention gate was measured on an A100, where it loses 61 % at 50K. In addition, the single-threaded compile setting was traced to a file that runs on every platform. One is AMD-wide, at a kernel line AMD named. One is a PCIe capability that hits bare metal too.

Half of the sixteen upstream threads belong to other people. The most useful role for this hardware was simply being the machine that upstream developers lacked.

3The four that are not this

The measurements that mattered most were the ones that took a finding off this list.

Two were settled by measuring another vendor Speculative decoding collapse at long context appeared to be an RDNA3 issue. When tested on a rented A100, however, the same model lost 61 % at 50K through the identical Triton kernel, and recovered on a backend without that guard. Similarly, a 128-expert MoE recorded at 15 tok/s initially suggested missing ROCm tuned kernels. The actual cause was an assignment in env_override.py that executes on every platform. See one report and the other.
One is AMD-wide, at a line AMD named Weight loading ran slower than disk reads because kfd_svm.c inspected the access mode directly from the VMA. A read-only copy requested write permissions, breaking copy-on-write across every resident page. That kernel file is not architecture-specific. AMD confirmed the underlying mechanism, and an independent user reproduced the failure on a different card. See the full write-up.
One is not about the GPU at all Every RCCL collective failed at dispatch because the PCIe root port above the card lacked the AtomicOps capability. This failure reproduces on bare metal and has no dependence on the installed GPU. For a virtual machine, the fix requires a single line of host configuration. See the RCCL write-up.

A fifth case warrants separate distinction because it reflects host topology rather than the silicon. The 2D attention path launches one workgroup per KV head. Splitting a model across two cards halves the available KV heads, causing compute starvation to double. That penalty is an inherent cost of tensor parallelism. The single-card control measured here — an A100 running the identical kernel — does not pay it. See the dual-card comparison.

4What the hardware turned out to be for

Sixteen upstream threads originated from this work. The split tells the story: eight are ours, while eight belong to external contributors where this test bench provided measurements they could not gather themselves.

That is the realistic value of consumer cards to this software ecosystem. The goal was never raw benchmark throughput: running on a VFIO guest without peer-to-peer over a cross-die PCIe 3.0 link establishes only a lower bound. Their genuine utility lies in bridging an empirical gap: providing the physical hardware that developers lack, allowing compile-only validation plans to be verified against live execution.

5What is not established

The classification is a judgement

While each magnitude recomputes and each note cites evidence, assigning findings to axes remains an argument. Two of the eight could occupy different columns: the W4A16 type gate is a bug located in an architecture-specific kernel, while the absent tuned MoE configurations are AMD-wide within an RDNA3 evaluation.

One machine, one software generation

Measurements reflect gfx1100 on a VFIO guest across two vLLM generations and two ROCm versions. Whether these findings apply to RDNA4 was not measured. The repository notes expect the gap to extend there, but that statement reflects documentation audits rather than benchmark runs.

Whether the gaps are closing

A single upstream pull request merged during this study, resolving half of one finding. That resolution indicates progress, but does not prove an ongoing trend. The data records where gfx11 support stood at the time of testing, not the velocity of upstream development.

2026-08-29 · a campaign that sorted into three of these bins at once Twenty configurations across the two Radeons and a rented A100 produced one finding in each category, putting this taxonomy into practice. Vendor-neutral: vllm#45450 has effect only when the patched Triton kernel is actively executing. Because Qwen3.8-27B bypasses that kernel on both platforms — selecting ROCM_ATTN here and FLASH_ATTN on CUDA — the patch remains installed but idle on each. AMD-wide: ROCm's selector opts for ROCM_ATTN because TURBOQUANT cannot run with the decoder. That choice concedes 15.0 % at 32K context that TRITON_ATTN — listed in the candidate options it displayed — would have preserved. And the middle case this article keeps finding: gemma-4 fails to serve on the 0.27 ROCm image entirely. An unsafe read occurs in vLLM's fallback getattr logic in model_arch_config_convertor.py, which expects AttributeError but receives transformers 5.x's custom exception instead; this branch is reached only because AMD's Quark plugin patches the config path. It is neither AMD's fault alone nor vLLM's alone.
