How much of this is RDNA3 being second-class

This repository's own summary says RDNA3 is a second-class citizen in ROCm's kernel ecosystem, and eight write-ups sit under that heading. Sorting them by what the evidence actually supports, three of the eight are that. The rest are AMD-wide, vendor-neutral, or not about the GPU at all — and knowing which is which is the difference between a diagnosis and a grievance.

__CHIPS__

Abstract

The claim is real and it is narrower than it looks. What survives as architecture-specific is a small, specific list: a fast attention path this hardware falls off, a native quantised-linear kernel whose type gate excludes a common checkpoint class, and a performance heuristic written into one architecture's branch of one function and not the other's.

The purest instance is one line. use_rocm_custom_paged_attention requires gqa_ratio >= 3 on gfx11 and >= 1 on CDNA, for the same kernel. In the excluded range that kernel is 1.84× to 7.28× faster than the fallback it is passed over for, and the excluded band overlaps the admitted one. The bound does not separate anything.

Four of the eight are not RDNA3 problems, and saying so is what the measurements were for. Two were proved vendor-neutral by measuring another vendor: the same attention gate loses 61 % on an A100 and the single-threaded compile setting is in a file that runs everywhere. One is AMD-wide, at a kernel line AMD named. One is a PCIe capability that hits bare metal too.

Half of the sixteen upstream threads belong to other people. The most useful thing this hardware turned out to be is a device the people fixing these things do not have.

3The four that are not this

The measurements that mattered most were the ones that took a finding off this list.

Two were settled by measuring another vendor Speculative decoding collapsing at long context looked like an RDNA3 story until the same model on a rented A100 lost 61 % at 50K through the same Triton kernel — and stopped losing it on a backend without the guard. And a 128-expert MoE recorded at 15 tok/s looked like ROCm's missing tuned kernels until the cause turned out to be a plain assignment in env_override.py that runs on every platform. One and the other.
One is AMD-wide, at a line AMD named Weight loading slower than the disk is kfd_svm.c reading the access mode off the VMA, so a read-only copy asks for write access and breaks copy-on-write on every resident page. That file is not architecture-specific, AMD confirmed the mechanism, and a stranger reproduced it on a different card. The article.
One is not about the GPU at all Every RCCL collective failing at dispatch is a PCIe AtomicOps capability on the root port above the card. It reproduces on bare metal, it has nothing to do with which GPU is plugged in, and for a virtual machine the fix is one line of configuration. The article.

A fifth is worth naming separately because it is about the shape of the machine rather than the chip: the 2D attention path launches one workgroup per KV head, so splitting a model across two cards halves them, and the starved path starves twice as hard. That is a cost of tensor parallelism, and a single card of any vendor running the same kernel does not pay it. The article.

4What the hardware turned out to be for

Sixteen upstream threads came out of this, and the split is the point: eight are ours, and eight are other people's, where what this machine contributed was a measurement they could not take.

That is the honest summary of what a pair of consumer cards is worth to this ecosystem. Not benchmarks — the absolute numbers here are a floor, on a VFIO guest with no peer-to-peer and a cross-die PCIe 3.0 path. What it is worth is being the device in the gap: the one a fix's author does not have, on which a compile-validation-only test plan can be turned into a runtime result.

5What is not established

The classification is a judgement

Every magnitude beside it is recomputed, and every "why" line names the evidence, but the assignment of a finding to an axis is an argument rather than a measurement. Two of the eight could reasonably be argued into a different column: the W4A16 type gate is a plain bug that happens to sit in an architecture-specific kernel, and the missing tuned MoE configurations are AMD-wide inside an otherwise RDNA3 story.

One machine, one software generation

Everything here is gfx1100 on a VFIO guest, across two vLLM generations and two ROCm versions. Whether any of it holds on RDNA4 is not measured; the architecture notes say the ecosystem gap extends there, and that sentence is a reading of supported-hardware lists rather than a measurement.

Whether the gaps are closing

One pull request merged during this work and closed half of one finding. That is one data point about direction and it is not a trend. Nothing here measures how quickly gfx11 support has moved, only where it stood.

6What has changed since

2026-07-14 · one of the three narrowed by itself vllm#40977 merged, adding a second native kernel that accepts the checkpoint type the first one refuses. The finding survives — eight of twelve asymmetric configurations still have no kernel on gfx1100 — but its headline example does not: the model that decoded at 11.41 tok/s does 37.32 on current main.
2026-08-20 · one was fixed by a distro, not by a report Canonical shipped the missing kernel commit in 7.0.0-30. The Launchpad bug asking for exactly that backport is still untriaged, so it came through the ordinary stable route. Reporting a thing and a thing being fixed are different events, and this repository has one of each.
