RDNA3 · vLLM · 实测于 2× RX 7900 XT

一个 kernel 就解释了
12.1 到 4.2 tok/s 的全部下滑

一个上下文越长解码越慢的混合 SSM 模型

线性注意力本该让长上下文变便宜。在这台机器上，Qwen3.6-27B 从 500 token 到 32 000 token 由 12.1 掉到 4.2 tok/s，而同一个下午测的稠密 8B 保住了 77 % 的短上下文速率。问题不在那 48 层线性注意力。 在剩下的 16 层。

2× RX 7900 XT · gfx1100 · TP=2 vLLM 0.23.1.dev1 · ROCm 7.14 VFIO 直通 · 无 P2P · 跨 die PCIe 3.0 测量批次 2026-07-25

摘要

一个混合 Mamba / gated-delta-net 检查点，在 500 到 32 000 token 之间丢掉 65 % 的解码速率， 曲线比同一台机器同一场 campaign 里任何稠密模型都陡十四到四十倍。

kernel 级 profile 把这段增长几乎全部指向一处：kernel_paged_attention_2d， 服务该模型 16 个全注意力层的 Triton 回退路径，单次调用成本涨 28.3 倍，而这一步里其余 kernel 全都持平或更便宜。 线性注意力层兑现了这个架构的承诺。

之所以走回退，是因为 ROCm 的自定义 paged-attention kernel 对这个模型在三个条件上都够不到； 之所以在这个模型上特别慢，是因为 batch=1 时只有 4 个 KV head，kernel 几乎没有可并行的东西。 两条独立信号一致：单卡功耗随深度下降，而按读取的 KV 字节数归一化后差距不是缩小而是拉大。

同一台机器同一天，同一个检查点在 llama.cpp 下的斜率浅 28 倍，这排除了驱动和硬件。 上游修复存在，这里测了两次，最近一次是 vLLM 0.27 上的受控 A/B：32 K 处 9.46 倍。 该 A/B 有一格是双峰的，文中如实报告。

1测了什么，怎么测的

第 2 节的全部数据来自同一场 campaign：一套软件栈、一个下午、所有模型都钉在上面。 五个架构、十一个上下文长度，292 次解码与预填充测量。每格由 vllm serve 提供服务， TP=2、开启 CUDA graph、--gpu-memory-utilization 0.85、512 token 输出，取两轮的均值。

速率报的是它自己那几轮的极差，而不是标准差。每格只有二到四轮，标准差给出的精度超过样本能支撑的程度； 极差占均值的比例说的是同一件事，又不必假定一个分布。图 1 每个点都带着它的轮数和这个极差，悬停可见。

关于绝对值怎么读 这是一台 VFIO 直通的虚拟机，两卡之间没有 P2P，走跨 die 的 PCIe 3.0，是刻意选的最不利拓扑。 本文里的形状可以迁移；绝对速率是下界，不是这套硬件的性能标定。

2观察到的现象

五个架构、十一个深度、一场 campaign。其中四个随上下文平缓下降，这是 KV cache 决定的、躲不掉的。 第五个不是这样。

混合模型在每个深度上都是绝对值最慢的——按参数量本不该如此——而且它是唯一一条向下弯而不是趋平的曲线。 保留率是更干净的统计量：其余每个配置在 32 000 token 处都保住了短上下文速率的 67 % 到 78 %， 这一个只保住 35.1 %。

换成斜率，也就是每多一个 token 上下文所增加的解码微秒数：混合模型 4.84 µs， 稠密 8B 0.118 µs。相差 41 倍，本文余下的篇幅都在解释这个数字。

3归因：是一个 kernel，不是这个架构

在两个深度上各做一次 torch profile，保持 CUDA graph 开启，并把 kernel 调用归属到它所落入的那个引擎步窗口， 以免 chunked prefill 的调用混进解码数字里。

48 个 gated-delta-net 层在 32 K 处和 1 K 处一样贵——0.95 倍——这正是线性注意力承诺的，也是这份实现交付的。 量化 GEMM 同样持平。只有一个 kernel 动了，而且动了 28.3 倍。

这笔账对得上。按每步 16 次调用，paged attention 从 5.71 ms/步涨到 161.5 ms/步，多 155.8 ms。 而解码步本身，从 CUDA graph 回放测得，从 85.85 ms 涨到 236.9 ms，多 151 ms。 paged attention 的增长解释了全部解码变慢；其余每个 kernel 在更长上下文下都持平或更快。

4为什么会走回退路径

那 16 个全注意力层落到 Triton 上，是因为 ROCm 的自定义 paged-attention kernel 拒绝了它们。 vllm/platforms/rocm.py 里 use_rocm_custom_paged_attention 的 RDNA 分支要求 （除其他条件外）head_size == 128 且 block_size == 16。

use_rocm_custom_paged_attention · 反事实调用
# 在运行中的引擎上测出来的，不是从 config 里读的
head_dim                = 256       # gate 要 128
cache_config.block_size = 784       # = 16 x 49，gate 要 16
is_pow2(784)            = False     # 在它自己那条路径上就否掉 use_custom
gqa_ratio               = 6         # 这一条是过的

# 单独放宽任何一个不满足的条件，仍然不够
use_rocm_custom_paged_attention(head_size=128)   -> False
use_rocm_custom_paged_attention(block_size=16)   -> False

没有任何单一条件是那个阻塞点。单独放宽其中一个，gate 依然关着； 而 chunked_prefill_paged_decode.py 还会独立地在 is_pow2 上否掉 use_custom。 自定义 kernel 在这里三重不可达——这就是为什么把回退路径改快是对这一类模型唯一管用的办法。

最容易想到的那个修法不成立 放宽 head_size 检查只是把失败挪个地方，不是移除它。 csrc/rocm/attention.cu 里的 CALL_CUSTOM_LAUNCHER_BLK_HEAD 只分发 case 64 和 case 128，其余一律 TORCH_CHECK。 这个条件是 kernel 的实际能力边界，不是保守的门槛。

5为什么回退路径在这个模型上特别慢

同一台机器上的稠密模型也走同一条 Triton 路径，却不会这样退化。差别在于 batch 为 1 的解码阶段， kernel 手里有多少可并行的东西。

4 个 KV head、batch 为 1，能铺到这张卡 84 个 CU 上的东西非常少。两条独立信号都指向占用率而不是工作量：

功耗随上下文增长而下降

518 token 时是 265 W + 265 W，24 K 时是 232 W + 227 W。这轮 sweep 里没有别的模型会随深度掉功耗； 其余模型都是往 265 W 爬然后停在那儿，只有这一个会掉回来。起始值本来就不同——518 token 时 8B 在 245 W、 12B 在 206 W、26B MoE 在 193 W——所以有意义的对比是方向，不是水平。是算力在空转，不是在饱和。

按 KV 流量归一化后差距更大

64 层里只有 16 层带 KV cache，而且 GQA 比例激进，所以这个模型读的 KV 是三者中最少的： 每 token 64 KiB，对 Qwen3-8B 的 144 KiB 和 gemma-4-31B 的 160 KiB。按每 KiB 读取量算， 它是 Qwen3-8B 的 92 倍、gemma-4-31B 的 36 倍。 所以不可能是"这个模型本来就更重"。

6对照：同一个模型换一个引擎

同一台机器、同一天、同一个检查点家族，只换推理引擎。如果崩溃来自驱动、GPU 或者拓扑，这里也该出现。

llama.cpp 的 ROCm 斜率落在稠密模型在 vLLM 下产生的那个区间之内；Vulkan 那条比这个区间还低，比它们里任何一个都更平。 于是有两个独立来源对"这台硬件上正常的斜率长什么样"给出了一致答案，而这一个配置比它高出一个数量级。

一个受扰动的点，说明而不是删掉 ROCm 的 16 384 那一点测出 21.35 tok/s，标准差 2.635，而其余各点都在 0.06–0.09； 而且更深的 24 576 反而更快。那一次测量受了扰动，不该单独拿来读。 它留在图里，是因为悄悄拿掉不方便的点比展示一个更糟。

与此同时，预填充的表现正如架构所承诺：吞吐随长度上升，从 500 到 32 K 是 805 → 880 tok/s， 而稠密模型在同一区间掉 8–44 %。反转的是解码。

7修复，测了两次

上游修复是 vllm#45916， 它给 Triton 回退路径加了一个 split-KV 解码 kernel：不再是每个 (序列, KV head) 一个 workgroup 走完整个上下文， 而是把 KV 区间切开分给更多 workgroup，之后再归约。这恰好是这个模型缺的那种并行度。

这里先在 7 月的 vLLM 0.23.1 上验证过一次——32 K 处 2.52 倍，单次差分、两侧深度略有不同—— 然后做了正式的一次：0.27 镜像上的受控 A/B，两臂同栈同 harness，每格一个全新容器，只换那一个 kernel 文件， 跑两遍并把两臂顺序颠倒。

两轮合并后：1 K 处 1.38 倍，8 K 处 3.52 倍，32 K 处 9.46 倍。 32 K 处解码从每 token 261.9 ms 降到 27.7 ms，斜率从 7.408 降到 每 1 000 token 上下文 0.262 ms，1 K 到 32 K 的保留率从 10.2 % 升到 70.0 %。崩溃消失了。

8没有被确立的部分

四条。因为一个只列自己成功之处的结果，不算测量。

A/B 有一格是双峰的

8 192 token 处，打了补丁的那一臂四轮给出 47.02、40.14、47.58、42.41 tok/s。排序之后， 相邻值之间的最大间隔大于总极差的一半，而且落在中间：这是相距约 15 % 的两个模态， 不是一个有噪声的数。加跑第三、第四轮让极差变宽了，从 15.8 % 到 16.8 %，不是收窄。 它不是 split-count 启发式——那是一个对配置固定住的输入而言的纯函数。机理没有确立。 上面引的 3.52 倍是四轮的均值，而它哪一簇都不描述。

一台机器

单机、单一厂商、全程 batch 为 1。占用率那套解释预测：batch 增大时崩溃应当减轻。这一点这里没有测。

这个修复没修掉的东西

paged attention 从解码步的约 68 % 降到 11 %。剩下的由量化 GEMM 主导，在短上下文时约占一个解码步的 77 %。 被解决的是斜率；基线是另一个问题，有另一个答案。

9此后发生的变化

本文是一份带日期的记录，不是长期有效的建议。上面的测量之后，有两件事已经变了。

2026-08-10 · gate 不再需要谁去放宽 7 月那次验证在本地把 on_gfx12x() 放宽成 on_gfx1x()，好让 gfx11 够得到新 kernel。 那个改动已于 2026-08-10 合入 vllm#45916 自己的分支，所以这个 PR 如今按其现状就接纳 RDNA3，本地什么都不用做。
2026-08-28 · 基线那个问题有答案了 7 月的写作稿收在"斜率解决了，基线是另一个问题"。图 4 的 0.27 A/B 回答了它： 32 K 处该模型现在跑 36.1 tok/s，对最初 campaign 测到的 4.2； 而残余斜率落进了这台机器上稠密模型产生的区间之内，不再高出 27 %。
2026-08-29 · 本文有两个数字和它自己的图对不上 摘要里写混合模型的曲线比稠密模型"陡四到四十倍"。对照图 3 画出的那个区间—— 每 token 0.118 到 0.339 µs——混合模型的 4.84 是陡 14.3× 到 41.0×： 下界是十四，不是四。另外"llama.cpp 的斜率落在区间之内"只对 ROCm 那条成立，Vulkan 那条是 0.107，整个落在区间以下。两处都已就地更正，verify_doc_figures.py 现在把这个比值和两个后端各自相对区间的位置都钉住了。
