被排除的 kernel 在六十个格子里全赢，
而两个区间还互相重叠

一道 2 到 7 倍的门，什么也没换来

在 gfx11 上，vLLM 的 ROCm 定制 paged-attention kernel 只在 query 与 KV head 之比至少为 3 时才启用。而在被排除的那个区间里，同一个 kernel 比它被越过去换来的 Triton 兜底快 1.70 到 7.28 倍，数值上又与之等价。 六十个格子、两个 vLLM 版本，无一例外。

2× RX 7900 XT · gfx1100 vLLM 0.23.1 与 0.27.1 外加一张跑同一份 Triton 源码的 A100 已提为 vllm#54210 实测 2026-08-28

摘要

这个界限随 vllm#17004 进来， 它自己的说明写着这个 kernel "支持 gqa_ratio 到 16，并在 gqa_ratio 为 3 或更高时相对现有 kernel 有性能收益"。所以它是一个性能启发式，不是能力限制； 同一个函数的 CDNA 分支从 ratio 1 起就跑同一个 kernel。这两点在 main 上今天依然成立。

真去测，这个启发式在这里是反的。六十个实测格子 —— 五种形状、六个上下文长度、两代 vLLM —— 定制 kernel 在每一个格子里都更快，而且被排除的区间与被放行的区间在两个版本上都重叠。 这道界限没有分开任何东西。

引出这件事的报告 vllm#50603 还把长上下文下的精度下降算在兜底路径头上。这一条不成立：两种架构上 90 个格子的相对误差都落在 2.12e-3 到 4.72e-3 之间，而且任意两个深度的汇总中位数相差不超过 1.09 倍。 而一条平坦的带子只有在仪器能看见故障时才有意义，所以给同一套测量喂了一个故障： 最后一个 KV tile 未写入尾部里的 NaN 会污染两条路径，而且只在跨过那个边界的长度上，别的长度都不会。

在真实模型上端到端，把那一行放宽在 1K 上值 1.02 倍，在 32K 上值 1.17 倍， 在较新镜像上以两种运行顺序各复现一次。这就是 vllm#54210，而本页是它的依据。

1测的是什么

两条路径都通过 vLLM 自己的 chunked_prefill_paged_decode 分发驱动， 只强制 use_rocm_custom_paged_attention 一个变量，所以两臂之间参数打包的方式完全一致。 纯 decode：每个序列一个 query token，上下文完全在缓存里 —— 这正是报告描述的形状。 参考实现是 fp32，而且是从分页之前的 KV 算的，不是从缓存里算的， 所以分页错误不会自己抵消掉自己。打分用相对 L-infinity， 以参考实现自身的尺度为基准，这才让不同长度之间可比。

形状集合覆盖 head size 128、block size 16 下的 ratio 1、2、3、4， 外加 32/16 —— 那是 gemma-3-27b-it 的真实形状，满足 gfx11 这道门除比值之外的每一个条件。 CUDA 对照编译的是同一份 Triton 文本：kernel 被原样提取到一个独立模块里， 启动参数照抄分发处的参数表。

2六十个格子，没有例外

论据是那两条带子，不是最大值。0.23.1 上被排除的比值跨 1.84× 到 7.28×，被放行的跨 2.35× 到 7.40×；0.27 上是 1.70×–6.05× 对 2.20×–6.05×。两个版本上两条带子都重叠—— 这就是"这道界限没有分开任何东西"这句话的一句话版本。

3精度那条主张，以及它下面的对照

原始报告描述了两个症状。第一个 —— 兜底路径被走到 —— 完全正确，上面所有内容都是关于它的。 第二个是兜底路径随上下文变差。这一条在这里可测，而且不成立。

一次干净的扫描，如果仪器是瞎的，就一文不值 上面那次扫描没有触及两件事：每个长度都是 block size 的整数倍， 所以最后一个 KV tile 从不跨过序列末端；而且缓存是零填充的。 把它填成 NaN、并使用会跨过边界的长度，就能按需造出这个故障 ——而且只在那里。
只有 NaN 会传播：1e4 这种有限的垃圾值单靠分数掩码就正确处理了，这正是它微妙的地方。 在这个版本上两条路径被污染的方式完全一样。

4放宽它在一个模型上值多少

kernel 微基准不是一个 PR 需要拿出来的东西。gemma-3-27b-it-w4a16， TP=2，开 CUDA graph，解码用 64 减 8 差分，每格一个全新容器， 这样源码改动不会在两臂之间泄漏：

路由是从 TP worker 内部记录的，不是推断的，每一格都记。那些全注意力层带着 head size 128、 block size 16、原生 KV 布局和 2 的幂 block 抵达，所以比值是它们唯一没通过的那个条件； 滑动层在两臂里都卡在 sliding_window == 0 上，从不移动。

这次测量不是什么 两臂输出是否相同不是正确性测试。在这台机器上，这个模型的 greedy 解码跨进程不可复现， 所以比较 token id 测的会是我们自己的非确定性。数值论证在图 2，对着一个 fp32 参考实现。 另外第一次尝试用的 kernel 计数器是瞎的，因为 TP=2 在 spawn 出来的 worker 里跑注意力， 父进程里的计数器什么也看不到。

5放宽它同时会放进来什么

打开一道门，门后的东西都会进来。 vllm#53856 修的正是同一个定制 kernel 里的一个真实故障：它给序列末端之后的 logit 打了掩码， 但它向量化的 V-cache 读取仍然吃掉整个最后一个 block， 于是尾部一个未写入的 NaN 会污染输出。它的测试计划写着 gfx11 只做了编译验证，因为作者没有这种设备。

强制那一列才是与这个提案直接相关的。绕过这道门之后，原样那一臂被污染的是八个格子而不是四个： 比值 2 在跨边界长度上以完全相同的方式失败，两种 dtype、只投 V 和 K+V 都失败。 八个在打了补丁的那一臂上全都干净。所以放宽这道门会把比值 2 放进这个 kernel， 而这就是它会一起放进来的那个故障—— 这也是为什么这两条 issue 该放在一起说， 以及为什么 gfx11 的运行时证据是应那个 PR 作者的请求送过去的。

6没有被确立的部分

报告里的第二个症状

这里排除掉的只是一个假设 —— Triton 2D kernel 随上下文增长而丢失精度。 报告者的模型是本项目没有的一个 VLM，跑在本项目没有的硬件上， 而这里测的是 kernel，不是他们的输出。他们那个症状仍然需要一个解释。

纯 decode、这些形状之外的一切

滑动窗口形状、fp8 KV、prefill 形状，以及 kernel 层面的 TP>1，这里都没有测。 端到端那次测量是 TP=2，但那是模型层面的测量，不是 kernel 层面的。

NaN 是怎么进去的

allocate_kv_cache 会把后备分配零填充，所以不是新分配的垃圾值； vllm#53856 把它归因于 sleep 模式和分配器行为。这个探针是故意注入的， 它只测量 kernel 之后会怎么做。

一台机器，以及 model runner 那个问题

这里的一切都在一台 gfx1100 上。一个相关问题 —— Model Runner V2 是否会走到同一道 guard —— 在这台硬件上测过，答案是会，37 行里有 36 行与 V1 完全相同； 但投机是否会让 MRv2 下的 decode 带上多于一行 query，无法测量， 因为这里没有任何 checkpoint 能在那个镜像上配置起来。那一半靠的是读代码。
