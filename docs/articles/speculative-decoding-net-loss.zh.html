一个布尔值，在 Radeon 上是 71 %，在 A100 上是 61 %

打开 vLLM 自己文档里写明支持的 MTP 助手，gemma-4-31B 在 1K 上下文下解码快 36.9 %，在 32K 下慢 70.8 %。原因不是草稿模型、不是硬件、 也不是接受率：投机把 max_seqlen_q 设成 2，而某个 or 链里的一句把这读成"这不是 decode"，于是 kernel 从 128 个 workgroup 掉到 8 个。

2× RX 7900 XT · gfx1100 · TP=2 以及一张 A100 80G · CUDA gemma-4-31B + 官方 MTP 助手 实测 2026-08-01 与 2026-08-26

摘要

vLLM 的文档把这个助手列为支持，并给出命令行，完全没提上下文长度。在四个深度上测下来， 效果是单调的，而且会变号：+36.9 %、−14.0 %、−32.4 %、−70.8 %。到 8K 就已经是净亏。

门是 Triton unified-attention 后端 use_3d 条件里的 max_seqlen_q > 1。3D kernel 把长 KV 序列切成段并行归约； 投机多出来的那一行 query 让它失去资格，于是 launch grid 从 1 × 8 × 16 变成 1 × 8。那一句上的注释说的是"这一批里有 prefill 请求"， 但真正的约束是缓冲区形状：段缓冲按序列分配、按 token 索引，只有在一行 query 时两者才重合。

三个看起来更像的解释，都测过，都否掉了。不是 KV head 太少：这个模型有 16 个， 不开投机时好好的。不是多出来的那行 query：直接调 kernel，从一行到两行在 32K 上一个构造下花 0.08 %，另一个构造下 0.16 %。不是分块参数：把上游给 Blackwell 调的那组常量移过来，反而慢 8.7 %。

这个论断说的是一个 kernel，不是一个厂商，所以它预言：任何被路由到同一个 kernel 的 CUDA 机器都会出现同样的塌陷，而没有这道门的后端不会。一张租来的 A100 把两条都测了： 在被强制的默认路径上 30K −28.2 %、50K −61.1 %，换到 FlashInfer 塌陷消失。 两条预言都成立。

1这条阶梯长什么样

gemma-4-31B-it-qat-w4a16-ct，TP=2，batch 1，greedy，官方的 gemma-4-31B-it-assistant，num_speculative_tokens: 1。 解码用同一深度下 64 token 生成减 8 token 生成的差分，与 prefill 分开。

vLLM 自己的计数器在 32K 上是 Mean acceptance length: 1.12，78 个草稿接受 9 个。 反推 1K 的加速意味着那里接受率大约 0.46，所以接受率也随深度下降。 这确实是一笔真实开销 —— 一个被拒的草稿仍然付了助手的一次前向和目标模型的一次验证 —— 但在助手只有四层宽的情况下，它撑不起 −70.8 %。第 5 节给出撑得住的那个。

2那一句

vllm/v1/attention/ops/triton_unified_attention.py
use_3d = not (
    seq_threshold_3D is None
    or ...
    or max_seqlen_q > 1          # 投机让它变成 2
    or num_seqs > seq_threshold_3D
    or is_batch_invariant
)

这一句决定的是：kernel 被允许用掉这块 GPU 的多少。

那一句上的注释说的是"这一批里至少有一个 prefill 请求"。真正的约束不是这个， 而这一点很重要，因为它决定了真正的修复长什么样。段缓冲分配成 [seq_threshold_3D, num_heads_q, segments, headdim] —— 按序列； 索引成 segm_output[token, head, segm_idx, :] —— 按token。 一行 query 时两者重合；两行时缓冲区会越界，于是这道门把它排除掉， 而 max_seqlen_q > 1 顺带把投机和 prefill 一起抓走了，因为它分不出这两者。

3只剩一个解释的那个对照

最直觉的读法是：两行 query 本来就是更多的工作。用这个模型的形状直接调 unified_attention，不加载模型也不开投机，扫 query 行数：

另外两个解释也测过并否掉了。KV head 太少： 混合 SSM 那篇里的塌陷来自只有 4 个 KV head， 而这个模型有 16 个，不开投机时没问题。分块参数：上游有一段 tuned_large_head，条件是 head_size == 256 and max_seqlen_q > 1， 被限定在 Blackwell 上，其余条件这台机器全都满足；把它的 BLOCK_M = 32 移过来，32K 反而慢了 8.7 %。

4另一个厂商

一个关于 kernel 的论断，会对它没测过的硬件做出预言。如果塌陷就是 3D 掉到 2D， 那么任何被路由到同一个 kernel 的 CUDA 机器都该出现它，并随上下文加深； 而没有这道门的后端不该出现。gemma-4 的 head 维度不齐， 所以只要 FA4 不可用，vLLM 就强制走 TRITON_ATTN —— 而 A100 没有 FA4。 于是这个预言只要花一小时的租用时间就能测。

5把投机放回 3D 路径之后值多少

手工把缓冲区加宽、把阈值抬到 2，32K 上从 8.85 恢复到 32.42 —— 投机终于赢过了不投机。 但那不是修复：它没法表达"投机的两行 query，但不要 prefill 的四千行"； 而且在 30K 提示下 greedy 输出从第 35 个 token 起与 stock 分叉，三个可能的成因当时没有分开。

vllm#45450 六月就开着、 卡在冲突上，而它正是那一节要的形状：门变成 max_seqlen_q > decode_query_len，prefill 仍被排除，段缓冲按 token 分配。

分叉那个问题也了结了。kernel 层的定输入对比，18 个用例，显示两条路径各自逐位确定， 而两者最多相差一个 bf16 ULP —— 在一行 query 下也是如此，而一行正是今天线上跑的行为， 两行、四行同样。第 35 个 token 的分叉是既有的 2D/3D 归约顺序重结合， batch size 在生产里本来就会切换它，不是这次准入带来的缺陷。

6谁报了什么

同样的 3D 掉 2D 最早由别人报出： vllm#48076，2026-07-09， 在一张 B200 上跑同一架构的另一种量化。那份报告的触发条件是同一条 or 链里的另一句 —— num_seqs > seq_threshold_3D，一个 batch 大小阈值 —— 它提议的修复从 SM 数推导这个阈值。那个修复够不到这里这个触发条件： max_seqlen_q > 1 与那个阈值无关，所以无论阈值怎么算，投机照样掉到 2D。 这里新的是第二个触发条件、它不同的成因，以及 RDNA3 上的实测。

2026-08-01 贴到了那个 thread，2026-08-26 贴到了 vllm#52049 —— CUDA 侧一份同模型同症状的报告。那位报告者确认显式选 FlashInfer 可以绕开它， 这与机理吻合：塌陷是这个 Triton kernel 特有的，而显式指定后端就绕过了那次强制。 ROCm 上没有 FlashInfer，所以在这台硬件上办法仍然是按深度决定开不开。

7没有被确立的部分

交叉点

在 1K 与 8K 之间某处，没有测。A100 那侧也有同样的缺口：测了 30K 和 50K， 而 MTP 在 FlashInfer 上何时不再划算，只框出了范围，没有定位。

重复

ROCm 这条阶梯每格一个进程。MTP 那一臂后来发现有第二次独立运行，隔了五周， 三个长深度一致到 0.45 % —— 但不投机那一臂一次也没有，而且接受率没有逐格记录。 A100 那个矩阵同样每格一次，跨两台 VM，会话之间的方差没有量化。

采样

这里的一切都是 temperature=0，也就是草稿与目标最容易一致的情形。 采样应当降低接受率、让投机更不划算，但两个厂商上都没有测。

每边一个模型

gfx1100、TP=2、一台没有 P2P 的 VFIO guest、一个 checkpoint；以及一张 A100、一张卡、 一个 checkpoint。机理是一个关于共享 kernel 的源码级论断， 支撑它的是两台机器给出一致结果，而不是其中任何一次单独的测量。
