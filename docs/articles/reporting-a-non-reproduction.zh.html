RCCL · ROCm · 一个否定结论 · 实测于 2× RX 7900 XT

上报者自己的脚本只数 rank 0，
用一个单边故障演示出来

怎么报告一个你复现不出来的 bug

有人报告说两张 gfx1100 上的某个集合通信会静默返回错误数据。你手上正好有两张 gfx1100。 它没发生。这句话本身几乎一文不值 —— 但它可以变得有价值， 靠的是三件与"多跑几遍"毫无关系的事。

2× RX 7900 XT · gfx1100 · VFIO 直通 RCCL 2.30.4 · ROCm 7.14 对照 2× W7800 裸机 实测 2026-08-27 与 2026-08-28

摘要

ROCm#6565 报告两张 W7800 上 all_gather 会静默返回错数据，根因定位到初始化时的一次 8 字节拷贝 —— 同步返回时它的载荷还不在显存里。在他们那边，RCCL 2.27.7 和 2.28.3 上都能确定性复现。 在这台机器的 2.30.4 上不能，八种配置、135 次冷通信器初始化都正确。

让这句话有意义的是三件事。一次覆盖了他们机理所指那些维度的扫描： 他们的机理专门针对几个并发初始化拷贝里的第一个，而这台机器默认建两个通道， 扫描把这个数从 1 一直扫到 16，并把传输从共享内存换到 socket。 把差异摆明：两台机器在平台、内核和 RCCL 版本上不同， 在 PCIe atomics 和 IOMMU 上相同 —— 那些显而易见的解释被点名，而不是留给读者去猜。 以及对"用别人的脚本跑出来的干净结果能说什么"给出诚实的界限。

第三件才是有意思的那件。他们的复现脚本在每个 rank 上都算了校验， 但只在 rank 0 上计数失败，所以只在 rank 1 上出现的损坏会打印 ALL CORRECT。于是这个否定结论比它被报告出去时更窄。 这一点在当晚就被披露，随后写了一个跨 rank 的变体、八个 arm 全部重跑， 并且这个盲点是在这台硬件上被演示出来的 —— 注入一个单边故障，而不是从源码上讲道理。

1为什么一次干净的运行通常什么也说明不了

"我这儿没问题"是 bug 追踪器上最没用的一句话。它同时兼容三种情况：报告者错了； 报告者没错但你没跑到那个配置；以及你的测试根本看不见这个故障。 要把它变成维护者能拿来用的东西，在按下发送之前得回答三个问题： 这个配置本来有没有可能暴露它、两台机器到底哪里不同、以及你的仪器对什么是瞎的。

第一个问题就是扫描要回答的那个。他们的机理不是"集合通信坏了"： 丢的是最先发出的那次拷贝，在通道 0 上，两个 rank 都丢，而通道 1 的那次落地了； 而且他们报告说，把同样的 分配 → memset → 8 字节异步拷贝 → 同步 → 读取 序列写成一个朴素的单设备版本，200 次都复现不出来。 所以并发的多设备初始化模式是必要成分，而一次从来没有几个并发初始化拷贝的运行，什么也没测到。

通道扫描是让这个否定结论可被采信的部分。这台机器默认建两个通道， 正是他们"第一个丢、第二个落地"那个观察所需要的形状； 强制成 1、4、8、16 会改变并发初始化拷贝的数量，而关掉共享内存会把传输换到 socket。 全部保持正确。

2把差异摆明，而不是留给读者

一个否定结论是关于某个空间里某一个格子的断言，只有说清是哪个格子它才有用。 那些相同的行和不同的行一样重要：如果这台机器缺 atomics， 或者他们有 IOMMU 而这边没有，维护者一句话就能把整件事打发掉。

3先给界限，再做演示

第一次扫描用的是报告者原样发布的脚本 —— 从 issue 正文里提取出来的，不是重敲的， 并附上 md5 供任何人核对。正是这个性质让一个否定结论对他们有价值， 而也正是它把那个缺陷一起带了进来。

rccl_allgather_truth.py · 它的形状
bad_list = [...]        # 每个 rank 都算
bad_into = [...]        # 每个 rank 都算
if rank == 0:           # 但只有 rank 0 计数、只有它打印
    if bad_list or bad_into:
        fail += 1

只在 rank 1 上出现的损坏被算了出来，然后被丢掉，而这次运行照样打印 ALL CORRECT。既然那 135 次通过全都是这个脚本的判定， 这个否定结论其实是"在 rank 0 上没有观察到损坏"。 这个缺口在评论发出去十小时之后被写进了仓库，在任何人提出之前。

解决办法不是去改他们的脚本。改它 —— 哪怕只是加一次归约 —— 会损失掉让这个结论对他们可信的那个唯一性质。所以原件原样保留并留下哈希， 在它旁边写一个变体，然后两个都跑。

然后是同样八个 arm、同样次数，走那个变体：又是 135 之 135，两个 rank 都正确。 那条注意事项不是被更小心地重述了一遍 —— 它被一个结果替换掉了。 而且两次扫描被检查为覆盖同样的 arm、同样的次数，因为在另一组集合上重跑替换不了任何东西。

那个数错了的检查，以及它为什么留在这里 第一版 arm runner 用 grep -c 数有多少个 rank 报告过，而它数的是行。 两个 rank 经常打印在同一行上，于是它把 20 次运行里的 6 次报成单边， 而实际上两个 rank 都报了。没有任何测量受影响，因为判定是在脚本内部 all-reduce 的 —— 但这和这一整个阶段存在的理由属于同一类错误，而且 一个会数错的检查比没有检查更糟。改成数出现次数就好了。

4那个没能起来的第二证人

原计划里还有一个不经过 PyTorch 的第二证人，用的是报告者的另一个复现器。 rccl-tests 对着这个容器的工具链干净地编出来了，benchmark 和验证目标文件里都确认有 gfx1100 代码对象，然后两次记录在案的 all_gather 都在 rank 1 上于数据初始化 kernel 处以 HIP failure: 'invalid device function' 中止。 加不加验证那一遍都一样失败，所以不是验证 kernel 的问题；脚本后面几条臂没有跑到； 而那份克隆停在的是针对 RCCL 2.30.4 的 deprecated 分支。

这一点作为限制被记录下来，而不是删掉，而且入库的是未过滤的日志。 更早的一次尝试是通过一个解析输出的包装器跑的；那个过滤器什么也没匹配上， 于是给每一个集合通信都打印了 FAILED，包括 PyTorch 测试通过了 135 次的那一个。 那份日志被故意没有保留 ——一行错误的判定留在那里，比没有日志更糟—— 取而代之的是原始重跑。

5没有被确立的部分

版本轴对平台轴

这台机器和他们的在 RCCL 版本以及平台上都不同， 所以这里一次干净的运行说不出是哪条轴起作用。有两次运行能把它们分开，而这两次我们这边做起来都不便宜： 报告者在他们机器上跑 2.30.4 —— 他们本来就从源码构建，这对他们只是几分钟； 或者这台机器跑 2.28.3 —— 那需要一个 73 GB 的镜像而这里只剩 40 GB， 而且会毁掉其他工作正在用的容器状态。两者都在源文档里点了名，免得下一个人重新发现一遍。

135 次冷初始化框住了什么

它框住了：这个缺陷不是 gfx1100 加 RCCL 的普遍现象，而且在这台硬件的 2.30.4 上， 在试过的任何传输和通道数下都不出现。它完全没有框住报告者自己的配置，而且也框不住： 在他们的机器上那是确定性失败。

第二个证人

只有一个复现器真的跑起来了。它是报告者自己的主复现器，这是对的那一个， 但有一条独立的第二路径会更好，而它在这里没能有用地构建起来。

6此后发生的变化

2026-08-27 · 那条界限在当晚就披露了 第一条评论报的是 135 之 135，没有带 rank-0 这个限定。这个缺口在大约十小时后被发现并写进仓库， 在任何人提出之前。
2026-08-28 · 界限被替换掉，而不是被重述 跨 rank 的变体写好了，八个 arm 以同样次数重跑，结果现在是两个 rank 都正确。 上游那条评论被编辑成带上跨 rank 那一列和注入检查，而不是把原文留在那里。
仍然开着 ROCm#6565 开着， 而 2.28.3 之上的版本至今没有任何人报告过任一方向的结果。这里只是一个对照格子，也只当作一个来提供。
2026-08-29 · "每一个集合通信"在已入库日志里只有一个 第 4 节原写 rccl-tests 编出来之后"每一个集合通信都在 rank 1 上中止"。 benchmarks/rccl-6565/logs/stage2b-raw.log 里只有两次调用，都是 all_gather_perf；那个目录下没有任何 reduce_scatter_perf 或 all_reduce_perf 的输出。scripts/stage2b_rccltests.sh 本来要跑六条臂， 而运行在第二条之后就停了。脚本的意图不等于已入库的证据——这正是本文要讲的那个区别。 另外，那次扫描原本被称作"一次本可以暴露它的扫描"；它覆盖的是他们机理所指的那些维度， 而注入演示的是检查器，不是故障本身。

这里的一切。报告者原样发布的脚本、跨 rank 变体、arm runner、 各阶段日志、注入日志和机器指纹都在 benchmarks/rccl-6565/。 本页的统计数由 verify_doc_figures.py 从那些日志里反解出来，它同时还检查第二次扫描覆盖的是与第一次相同的 arm 和相同的次数。
